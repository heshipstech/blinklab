# LEARNING.md

One plain English note per increment. Written for the human, not for the machine.

## 0.1 Working documents before code

The concept this increment teaches is the working document. Before writing code, we wrote four short files that act as contracts.
PROJECT.md says what we are building and, just as important, what we refuse to build. SPEC.md says how the parts must talk to each other. ROADMAP.md is the ordered list of small steps. STATE.md is a ten line snapshot of where we are.
Why this matters: software goes wrong most often not in the typing but in the deciding. When decisions live only in someone's head, every session starts with re-deciding, and re-deciding drifts.
These files also solve a practical problem: an AI assistant has no memory of past sessions unless something on disk carries it. STATE.md is that carrier. Reading three files replaces an hour of "where were we".
This idea comes back in every single session, because every session starts by reading these files. It also comes back at increment 0.8, where an ADR (architecture decision record) does the same job for decisions that are expensive to reverse.

## 0.2 The toolchain: one tool, two jobs

The concept this increment teaches is the toolchain, here a tool called Vite.
Browsers do not understand TypeScript. Someone has to translate it into JavaScript before the browser sees it. Vite is that someone, and it has two modes.
`npm run dev` starts a development server. It translates files the moment you save them and refreshes the browser for you. Nothing is written to disk. This is the mode you live in while building.
`npm run build` is the shipping mode. It translates everything once, squeezes it small, and writes the result into the `dist` folder. That folder is what a web host actually serves. Ours is currently 0.83 kilobytes.
The other new thing on disk is `package-lock.json`. You never edit it. It records the exact version of every installed package so that another machine installs precisely the same thing. It matters at increment 0.5, when a build machine that is not yours has to reproduce your setup.
Why we wrote five files by hand instead of using a generator: a generated template arrives with code nobody asked for, and the project rule is that every line must be explainable. Our whole app is currently seven lines in `src/main.ts`, and you can read all of them.

## 0.3 Static analysis: machines that read code without running it

The concept this increment teaches is static analysis. Three different machines now read every line before any human does, and each catches a different kind of mistake.
Prettier is the formatter. It only cares how code looks: indentation, line width, quotes. Its value is that style stops being a discussion. Nobody ever reviews spacing again.
ESLint is the linter. It looks for patterns that are legal but suspicious, an unused variable, a comparison that is always true. Crucially, it also enforces rules we invent ourselves.
TypeScript in strict mode is the typechecker. It tracks what kind of thing every value is, and refuses code where a number could secretly be missing or a name could be misspelled.
Our own invented rule is the most important line of configuration in the project: files in `src/core` cannot import from `io` or `ui`, and cannot touch `window`, `document` or `navigator`. That fence is what will keep every measurement function testable without a camera. We proved the fence works by writing a violating file and watching lint fail with our own error message, then deleting it.
One real world lesson came free: we had to step TypeScript back from version 7 to 6.0.3, because the lint plugin does not support the brand new compiler yet. Tools travel in convoys, and the slowest ship sets the pace.
This all comes back at increment 0.5, when CI runs these same three machines on every pull request, and at 0.4, when the first protected `core` function appears.

## 0.4 The unit test: a claim that can lose

The concept this increment teaches is the unit test, through the smallest possible example.
Our function `distance` is pure: give it the same two points, it returns the same number, and it touches nothing else in the world. Purity is what makes testing trivial. There is no camera to fake and no page to load, you call the function and look at the answer.
The first two tests state ground truth: the distance from a point to itself is zero, and the corner points of a 3 4 5 triangle are exactly 5 apart. Maths knows these answers, so the test is not our opinion.
The third test states a property: the distance from a to b equals the distance from b to a, whatever the points are. Property tests catch mistakes that example tests miss.
A test only earns its keep if it can lose. We proved ours can: flipping one minus sign to a plus inside the function made a test fail within milliseconds. A test that passes no matter what is decoration, not protection.
We also widened tsconfig so test files are typechecked. A test file with a type error would otherwise lie quietly.
This comes back constantly: increment 3.1 builds the eye aspect ratio on top of this exact `distance` function, and every threshold in the blink logic will get the same three part treatment, below, at, above.

## 0.5 CI: a stranger's computer judges every change

The concept this increment teaches is continuous integration, CI for short.
Until now, "all gates pass" meant they passed on one specific Mac, with its particular Node version, its installed tools, and any local files that never made it into git. CI removes that asterisk. On every pull request, GitHub rents us a fresh Linux machine that has nothing, checks out only what is committed, installs only what the lockfile names, and runs the exact same five commands we run locally.
The key line is `npm ci` instead of `npm install`. Plain install is allowed to make choices, ci (clean install) is not: it reproduces the lockfile exactly or fails. This is the moment increment 0.2's lockfile earns its keep.
The deeper shift is social, even in a team of two like ours. Before CI, "does it work" was a claim a person makes. After CI, it is a fact a machine certifies, visible to any stranger reading the repository. The green check is the project's reputation, rebuilt from zero on every change.
And because the workflow triggers on pull requests, the pull request that introduced it was judged by it. The test of the test machine was the test machine.
This comes back at 0.6, where branch protection makes the green check mandatory rather than polite, and at 0.7, where a second workflow deploys the page to a public URL.

## 0.6 Conventions become mechanisms

The concept this increment teaches is the process gate: the difference between a rule people follow and a rule the system enforces.
Until today, "main only changes through reviewed pull requests with green CI" was a convention. We followed it every time, but nothing stopped a tired Sunday evening push straight to main. Branch protection turns the convention into a mechanism. GitHub now rejects direct pushes, rejects merges without the green check, and rejects force pushes, for everyone, including the repository owner, including me.
A rule you must remember is a hope. A rule the machine enforces is a guarantee. Guarantees compound: because main provably always passed CI, anyone can pull any commit of main and trust it.
The same idea, softer, drives the templates. A blank issue box invites vague issues. A template with headings, what happened, what should have happened, first failing observation, does the remembering for you.
Enforcement has a price, and we paid it immediately: my little post merge STATE.md pushes to main are now impossible, so STATE.md travels inside each pull request already written in its final form. When a gate inconveniences you, that is the gate working.
This comes back every single increment from now on, and especially at 8.6 and 8.7, where coverage floors and performance budgets become mechanisms the same way.

## 0.7 Deployment: the dist folder goes public

The concept this increment teaches is deployment, which for a site like ours is less mysterious than the word sounds.
Our app has no server. `npm run build` produces the `dist` folder, a handful of plain files, and "deploying" means copying those files to a computer that answers web requests. GitHub Pages is that computer, for free. The new workflow does the copy on every merge to main: build on a clean machine, hand `dist` to Pages, done. Merging to main and publishing to the world are now the same motion.
The one real lesson lives in `vite.config.ts`, and it is the subpath problem. Our site is not at the root of a domain, it lives under `/blinklab/`. A page that asks for its script at `/assets/app.js` gets a 404 (not found) there, and renders blank with no error you would notice. The `base` setting makes every generated URL start with `/blinklab/`. Blank page on a fresh deploy, wrong base path, is one of the most common deployment bugs on the entire internet, and now you have seen the cure before ever hitting the disease.
Note what deploys: `dist` only. The TypeScript, the tests, the documents stay in the repo. Visitors receive only the translated result.
This comes back at 8.7, where the size of what we deploy gets a budget, and every increment from now on, because each merged pull request updates the public demo.

## 0.8 The ADR: decisions have worse memories than code

The concept this increment teaches is the architecture decision record, ADR for short.
Code remembers itself, git holds every version forever. Decisions do not. Six months from now the code will show _that_ we use MediaPipe, but nothing in the code shows _why_, or what we rejected, or what we knew it would cost us. That context evaporates first, and its absence is how projects end up re-fighting settled questions or, worse, cargo-culting choices nobody can defend anymore.
An ADR is a small dated note with a fixed shape: the situation, the options actually on the table, the choice, and the consequences we accepted, good and bad. The bad consequences are the valuable part. Writing "we are bound to MediaPipe's landmark quality" today means that when that limit bites in Phase 3, it arrives as something we chose, not something that ambushed us.
Two rules give ADRs their strength. They are written only for decisions that are expensive to reverse, so the folder stays short and important. And they are never edited after merge, only superseded by a newer numbered ADR, so the folder is an honest history, not a polished story.
This comes back whenever we are tempted by a framework or a charting library, both of which now require a superseding ADR by their own rule, and at 7.3, where choosing a dataset gets the same treatment.

## 1.1 The impure edge: code that touches the world

The concept this increment teaches is the impure edge, the `io` folder, and why its code lives by different rules than `core`.
`distance` in core is pure: same input, same output, nothing else happens. Camera code is the opposite in every way. It asks for hardware that may not exist, triggers a permission dialog we do not control, and its outcome depends on a human clicking Allow or Deny. It cannot be pure, and that is fine, something has to touch the world. The architecture rule is only that such code stays quarantined at the edge, in `io`, so the measurement maths never inherits its unpredictability.
The permission model matters too. A page cannot take the camera, it can only ask, and the browser insists a human answers. We start the camera from a button click rather than on page load for the same reason in reverse: a permission dialog that ambushes a visitor before they know what the page is feels hostile, and browsers increasingly punish it.
Testing changes character at the edge. Core logic gets unit tests measured in milliseconds. Edge code gets the manual script in test/MANUAL.md, run by a person with a face and a light source. Notably, the deny path was still verifiable by machine: my test browser refuses cameras outright, which proved a rejected permission shows a readable line instead of a crash.
This comes back at 1.2, where the deny and no-camera states get proper readable treatment, and at 2.1, where the model loading joins the same impure edge.

## 1.2 The state machine: name every situation

The concept this increment teaches is the explicit state machine.
Before today, the camera's situation lived in scattered clues: a hidden attribute here, a text string there. That works until two clues disagree, a visible video and an error message at once, and nobody can say which is lying. The fix is to name every situation the system can be in, exactly one at a time: idle, requesting, running, denied, noCamera, failed. The whole page is then drawn from that one value by a single `render` function. If the state is right, the screen cannot be wrong, because the screen is a consequence, not a collection of separately maintained facts.
TypeScript enforces the "exactly one" part. The state is a union of shapes, and the message function must handle every shape or it does not compile. Adding a seventh state tomorrow would instantly flag every place that forgot about it.
Note where the pieces live. Classifying an error name into a state, and choosing a sentence for a state, are pure functions in `core`, tested in milliseconds. Only the thin click handler in `main.ts` touches the real camera. We split the decision from the doing, and the decision is the part that gets tested.
One defensive detail: an error name we have never heard of becomes a real `failed` state carrying its reason, never a crash. Browsers disagree on error names, and honesty about "I do not know what happened" is itself a state.
This pattern returns at 2.5 for the wrong landmark count guard, at 3.8 for the head pose validity gate, and at 4.6 for the frame rate honesty gate. Most of this project is deciding what state we are in and refusing to pretend otherwise.

## Fix #22: a bug fix is a workflow, not an edit

The concept this fix teaches is the bug fix workflow, because a good fix has stages and each stage exists for a reason.
It started with an observation by the project owner: the preview looked squeezed. That became an issue with the observation quoted verbatim and the diagnosis marked as a hypothesis, not a fact. Then the fix branch opened with tests named after the bug, written before the cure, so the repo permanently remembers what went wrong.
The technical cause had two halves. We requested a camera with no size preferences, and browsers then often hand over an old fashioned 4 to 3 picture from a camera that is naturally 16 to 9. And we pinned the element to a guessed width. The cure also has two halves: ask the camera for 1280 by 720 as an ideal, and size the element from the stream's real reported dimensions through a pure, tested function. "Ideal" is the honest word in that API, it is a negotiation, the camera gives the closest thing it can, and our layout function handles whatever arrives, including 4 to 3, without distortion.
The last stage belongs to the person who reported the bug: only their eyes can close the loop, which is why the manual script now demands proportions matching FaceTime.
One process lesson rode along. The previous increment's LEARNING note was edited but never committed, because a hand typed file list missed it. Checklists claim, git status verifies. The habit now is a clean status check before every pull request.

## 1.3 The injected clock: time as an argument

The concept this increment teaches is the injected clock, the rule from SPEC.md that time always arrives as a parameter.
Frames per second sounds like it needs a stopwatch, and code with a stopwatch inside is miserable to test: you would have to actually wait, and a busy laptop would make the same test pass today and fail tomorrow. Our QA rules ban that outright, no flaky tests, no sleeps.
The escape is to split the question. "What time is it" stays at the impure edge: the browser's frame loop hands us a timestamp per frame, we never ask for one. "What do these timestamps mean" is pure arithmetic in `core`: keep the last two seconds of them, then divide. In the tests we simply write timestamps down by hand, eleven stamps spaced 100 milliseconds apart, and the answer must be exactly 10, forever, on any machine, in zero milliseconds of waiting.
The fencepost detail is why the tests use countable numbers: eleven timestamps are ten intervals. Dividing by eleven would read plausibly and be wrong by ten percent, which is exactly the kind of mistake a reader cannot spot but a hand checked test cannot miss.
One discovery from verification: browsers pause the animation loop entirely for hidden tabs, my embedded test browser lives permanently in that state, so the live number can only be confirmed by a human with a visible window.
The injected clock returns everywhere time appears: blink durations at 4.3, rolling windows at 4.4 and 6.1, and the honesty gate at 4.6 that reads this exact fps number before daring to report a blink.

## 1.4 The canvas: owning the pixels

The concept this increment teaches is the canvas, and the ownership shift it brings.
Until now the browser displayed the camera stream for us. A video element is a black box with a picture inside: convenient, but closed. You cannot write on it, measure it, or decide what appears. The canvas inverts the deal. It is an empty rectangle of pixels that shows nothing unless code paints it, and now our frame loop paints the current camera frame onto it, sixty times a second.
To the eye nothing changed, and that is the point of the increment: prove we can reproduce reality before we start annotating it. The right-click test in the manual script is the tell, the browser now offers image options, because as far as it knows this is just a picture we drew.
Why go to this trouble: increment 2.2 wants to draw 478 landmark dots on top of your face. You cannot draw on a video element, but a canvas takes dots, lines and heatmaps as happily as it takes camera frames, all in the same paint call sequence.
Note the gating: we only draw while the state machine says running, and only after the canvas was sized from the stream's real dimensions. Drawing from a frameless video or onto an unsized canvas produces black or stretched output, the same class of silent wrongness the aspect ratio bug taught us to distrust.
This surface is where the rest of the project happens: dots at 2.2, the eye region at 2.3, sparklines at 3.2, fixation circles at 5.7, the heatmap at 5.9.

## 1.5 Normalise the world at the edge

The concept this increment teaches is the boundary mapper: raw data from the outside world gets cleaned into our own shape by a pure function, before anything else touches it.
The browser's device list is honest but messy. It mixes cameras with microphones and speakers, and until the user grants permission, every label is an empty string, a quirk that exists for privacy, so websites cannot fingerprint your hardware before you trust them. Feeding that mess straight into the page invites the mess to spread.
Instead, `cameraOptions` swallows the mess once: it keeps only cameras and turns blank labels into "Camera 1", "Camera 2". Everything after it deals only in our clean shape. The rule of thumb: the further a mess travels into a program, the more places know about it. Stop it at the door.
The mapper also carries the picker's business rule, more than one camera or no picker at all, as its own tiny tested function. The test file covers zero, one and two cameras, because "more than one" is a threshold, and thresholds get all three sides tested.
A design consequence worth noticing: the picker can only fill itself after the first successful camera start, since labels are blank before permission. That ordering came from the browser's privacy model, not from our code, and the code simply respects it.
Boundary mappers return in force at 2.1, where the landmark model's raw output crosses into our FeatureRecord world, and at 7.2, where a CSV loader does the same for the analysis track.

## 1.6 Six numbers that move a world

The concept this increment teaches is the transform matrix, the standard way graphics systems describe moving, scaling and flipping in one object.
Mirroring sounds like it needs pixel work, copy every row of the image reversed. Nobody does that. Instead you tell the canvas: before you draw anything, run every coordinate through these six numbers. Our mirror is `a: -1` (x runs backwards) and `e: width` (then shift it back into frame). The picture flips because the coordinate system flipped, the pixels were never touched.
The reason this deserves its own `core` module instead of two magic numbers in the draw call: the same matrix must apply to everything that lands on that canvas. At 2.2 we draw 478 landmark dots over your face. If the picture is mirrored and the dots are not, every dot sits beside the feature it belongs to, a bug you would stare at for an hour. With the matrix in one tested place, picture and dots cannot disagree.
The tests do not check the six numbers as trivia, they push actual points through: the left edge must land on the right edge, the centre must not move, and mirroring twice must hand back the original point. Properties, not opinions.
Why mirrored is the default: people have watched themselves in mirrors their whole lives. An unmirrored self view feels subtly wrong before you can say why. But the measurements in later phases work on unmirrored coordinates, the mirror is a display courtesy only, which is exactly why it lives at the drawing edge and not inside any maths.
This matrix returns immediately at 2.2 as the landmark projector, and its inverse thinking returns at 5.4, where screen points must map back into camera space.

## 2.1 A neural network is a file

The concept this increment teaches is what a machine learning model actually is at rest: a file of numbers, and an engine that runs it.
The `face_landmarker.task` file is 3.7 megabytes of learned weights, the distilled result of Google training on faces. It does nothing by itself, like sheet music without an orchestra. The orchestra is the WASM runtime, 33 megabytes of compiled inference engine that the browser executes at near native speed. Load both, and you get a function: hand it a video frame, get back landmark positions. That is all "running a model" means.
Both artefacts now live on our origin, the model committed to the repo, the WASM copied from the version locked npm package before every build. ADR-0002 records why: our privacy stance forbids the running app from calling anyone. Today we proved it, the network log during a full model load showed zero third party requests. A promise in SECURITY.md is a claim, an empty network tab is evidence.
Note the asymmetry the code respects: loading is slow and happens once, inference is fast and happens per frame. And note what `core` sees: nothing of MediaPipe. The presence predicate defines its own small shape of the result, so the vendor stays quarantined at the edge like the camera before it.
The lint gate also earned its keep today, by red flagging seven thousand lines of copied vendor code until it was told that vendor code is not ours to judge.
This is the foundation of everything in Phases 2 to 6: dots at 2.2 are these landmarks drawn, blinks at 4.x are these landmarks moving, and the 30 millisecond budget at 2.6 is this engine timed.

## 2.2 A point is meaningless without its space

The concept this increment teaches is the coordinate space, the silent assumption behind every x and y.
The model reports landmarks in normalised space: 0 to 1 across the frame, whatever its size. The canvas wants pixels. The display may additionally be mirrored. Three spaces, and a point only means something when you know which space it lives in. The bugs of this domain are all space confusion: draw normalised values as pixels and all 478 dots huddle in the top left corner, apply the mirror twice and the mask floats beside your face.
The defence is a single bridge. `projectNormalizedPoint` is the only road from model space to screen space: scale by the canvas size, then through the exact same mirror matrix the picture uses. Because picture and dots cross the same bridge, they cannot disagree, toggling Mirror flips them together by construction, not by carefulness.
The fixture tests pin the bridge with points a human can check while reading: the centre of the frame must land at the centre of the canvas, the top left corner at the top left, and under mirroring only x flips while y holds still.
Notice also what stayed where: the projector decides coordinates and lives in `core`, fully tested. `drawDots` only paints what it is handed and lives in `io`, untestable and trivially simple. Decisions in the testable place, actions at the edge, the same split as ever.
Spaces multiply from here: 3.4 adds millimetres, 5.2 adds screen regions, 5.4 maps gaze back from screen space toward camera space. Every one of those conversions will be a small pure bridge like this one.

## 2.3 Magic numbers get names and guards

The concept this increment teaches is the named constant, and why a list of numbers deserves tests.
The model's 478 landmarks come as an anonymous array. Landmark 159 is a spot on an upper eyelid, but nothing in the code said so until today, the knowledge lived in MediaPipe's documentation and nowhere else. Numbers used bare like that are called magic numbers, and they rot: six months on, nobody remembers why 159, and nobody dares change it.
So the eye indices moved into `core/constants.ts` under names, with a comment settling the classic trap: left means the subject's left, which appears on the right side of an unmirrored image. Every eye measurement for the rest of the project reads from these two lists.
Then the unusual part, we wrote tests for constants. Tests for data, not behaviour: the two eyes may not share an index, every index must exist inside the model's range, no index may repeat, and both eyes must have equal point counts. None of that proves index 159 is truly an eyelid, no test can, only your eyes on the canvas can. But the tests do make the cheap typos impossible, and the manual check covers the expensive one.
The quiet importance of this increment: from now on the code does not see 478 dots, it sees eyes. Naming a subset is the first act of measurement.
These lists come back instantly: 2.4 adds the iris rings beside them, 3.1 computes the eye aspect ratio from exactly these points, and 2.5's guard leans on LANDMARK_COUNT.

## 2.4 The ruler you were born with

The concept this increment teaches is the anatomical constant, and why ten orange points deserve their own increment.
Here is the problem they will solve. Every distance we can measure on the canvas is in pixels, and pixels lie: lean toward the camera and your eye grows fifty percent without opening at all. Phase 3 needs a way to turn pixels into real world units that hold still while you move.
The trick is that adult humans carry a built in ruler. The visible iris is close to 11.7 millimetres across in almost everybody, one of the most stable measurements in the human body, it is essentially adult sized from early childhood. If we can see how many pixels the iris spans, we know how many pixels a millimetre is, in this frame, at this distance, updated sixty times a second. That division is increment 3.4, and today's ten landmarks, a centre and a four point rim per iris, are its raw material.
So this increment looks cosmetic, orange rings sliding over your irises, but it is really instrument calibration: we are visually confirming that the model tracks the one feature whose true size we know. Watch the rings while you look around, their steadiness is the ceiling on every millimetre number this project will ever report.
One code note: "the ring is closed" became a data test, each ring must be exactly the four indices after its centre, which pins the topology assumption we took from MediaPipe's documentation.
The iris returns at 3.4 as the pixel to millimetre bridge, at 5.1 as the gaze pointer, and in Phase 9's pupil ideas.

## 2.5 The guard that should never fire

The concept this increment teaches is the trust boundary guard, a check written precisely because it looks unnecessary.
Our code trusts the model to return 478 landmarks. That trust is currently justified: ADR-0002 vendored the exact model file into the repo, it cannot change behind our back. So why guard? Because the dangerous day is not today, it is the future afternoon someone upgrades the model file in an otherwise innocent pull request. MediaPipe's older face mesh returns 468 points, no irises. On that day, without the guard, nothing would crash. `pickPoints` would skip the ten missing indices, the orange rings would vanish, and every millimetre computation downstream would quietly work with nothing. Silent wrongness again, the most expensive kind.
The guard converts that silence into a sentence on screen naming both numbers, and stops measurement, our null-over-guessing rule applied to a whole subsystem.
Two honest notes about testing it. First, the fixture: the tests feed a generated 468 point face, we do not need the real old model to test the decision, only its shape. Second, the limit: no end to end test can trigger this state, because the vendored model always returns 478. The pure decision is fully tested, the two line display wiring is covered by review, and the manual script documents why there is nothing to see. Claiming more coverage than exists would be its own kind of silent wrongness.
Guards like this multiply at every trust boundary from here: 3.8 rejects untrustworthy head poses, 4.6 refuses blink numbers at low frame rates, 7.2 will distrust every CSV row it loads.

## 2.6 A budget nobody watches is a rumour

The concept this increment teaches is the visible performance budget.
SPEC.md has said "inference under 30 milliseconds per frame" since day one. Until today that sentence was a hope, nothing measured it, so nothing could violate it. Performance rules that live only in documents always pass. Now the cost of every model run is measured, averaged and printed beside its budget, permanently. The moment a future change makes inference slow, the page itself will say so, to whoever is looking, including strangers on the live demo.
Two craft details. First, smoothing: a single frame's timing jitters, the operating system wanders by, the GPU pipeline hiccups, so the display shows the mean of the last sixty samples, steady enough to read, fresh enough to trust, one second of history at sixty frames. Second, boundary honesty: the budget test asserts that exactly 30 is calm and 30.1 complains, thresholds get all three sides tested, our oldest QA rule.
Note also what this number quietly settles: the console line from your screenshot claiming a CPU delegate. Instead of arguing about which processor runs the model, we read the price tag. If the mean sits comfortably under 30, the question is academic. If it does not, we have evidence, not vibes.
The measured-not-assumed idea returns at 7.8, where latency gets formally recorded in the README, and at 8.7, where this budget becomes a CI gate that can fail a pull request.

## 2.7 Reality, frozen for replay

The concept this increment teaches is the recorded fixture, the third and final kind of test data this project uses.
Synthetic fixtures, like our 3 4 5 triangle and the generated 468 point face, have ground truth by construction: we know the answer because we built the input from the answer. Their weakness is politeness, synthetic data never contains the noise, jitter and asymmetry of the world. Recorded fixtures are the opposite: five real seconds of a real face through a real camera, blinks and micro movements included, with no ground truth other than "this actually happened". The strongest test suites use both, synthetic data to pin the maths, recorded data to confront it with reality. Phase 3 will do exactly that.
Three craft details rode along. Precision costs bytes: raw landmark floats carry seventeen decimals of noise, rounding to four kept a tenth of a pixel and cut the file from fifteen megabytes to three. Tools can be too honest: my first version of the recorder shipped its button to production merely hidden, and the grep check on the build caught it, hidden is not absent. And assertion count is a performance number too: sweeping 143,400 landmarks with individual assertions cost three seconds per test run, counting violations in plain code and asserting zero restored the milliseconds culture.
The fixture returns immediately: 3.1's eye aspect ratio will run against these 300 frames, and any real blink you made during those five seconds becomes Phase 4's first honest test case.

## 3.1 The first measurement, and why it is a ratio

The concept this increment teaches is the eye aspect ratio, and through it, why good measurements are so often ratios.
EAR is two vertical distances across the eye, averaged, divided by the horizontal width: roughly 0.3 when your eye is open, collapsing toward zero as the lids meet. Six landmarks, three distance calls, one division, all built on the `distance` function from increment 0.4, which was the plan all along.
The division is the clever part. Raw eyelid distance is measured in pixels, and pixels inflate when you lean toward the camera, an eye can "open" fifty percent without moving. But leaning inflates the eye's width by the same factor, so the ratio cancels the distance out. Our scale invariance test states this as a property: double every coordinate and EAR must not budge. Ratios buy robustness by giving up units, EAR is a pure number, not millimetres, which is why 3.4 still needs the iris ruler for absolute aperture.
The fixture test was the increment's true examination: the formula ran over your 300 recorded frames and had to find your real blinks, the minimum EAR diving under half the median. It did. Synthetic shapes pinned the arithmetic, your face confirmed the meaning, both kinds of fixture doing exactly the jobs 2.7 assigned them.
And the ritual's loose end now has a name: whether your shallow third blink counts is a threshold decision on this exact number, which is increment 4.1's opening problem.

## 3.2 Drawing data honestly

The concept this increment teaches is the honest chart, through the two decisions every chart maker faces and most tools hide.
First, the scale. A chart that auto fits its axis to the data makes every wiggle fill the frame: sitting still would look as dramatic as blinking. Our sparkline fixes the scale at 0 to 0.6, so a blink always has its true visual size, and a calm minute truly looks calm. Auto scaling flatters, fixed scales inform.
Second, the gap. When you cover the camera, there is no measurement. The tempting shortcuts, drawing zero, or bridging across the hole, would both be lies: zero says "eyes fully closed", a bridge says "nothing happened". Our null samples split the line into separate segments, so missing data looks missing. This is the null-over-guessing rule made visible, the chart version of the honesty the maths has practised since 1.3.
Underneath sits the ring buffer, the standard answer to "the stream never ends but memory must": push forever, capacity stays fixed, the oldest samples fall off the front. The timing module from 2.6 already needed exactly this, so its own push now delegates to the shared one, reuse instead of a second copy.
And the fixture keeps earning: one of the tests feeds all 300 recorded frames through the sparkline and requires a single unbroken segment, your five seconds becoming the chart's first regression test.
Hand drawn charts return at 5.9's heatmap and 6.6's contribution panel, and this exact sparkline becomes the backdrop on which 4.1's blink detector draws its threshold line.

## 3.3 Ground truth by construction

The concept this increment teaches is the answer key, and how to build one when reality refuses to provide it.
The next increments make physical claims: your eyelid opening is so many millimetres, your head is tilted so many degrees. How would a test check that? Your recorded fixture cannot help, nobody knows the true millimetres behind it, reality comes without labels. So we build faces from arithmetic instead: a tiny 3D model with the true anatomical sizes typed in, iris 11.7 millimetres, eye width 30, pupils 63 apart, rotated by chosen angles, placed at a chosen distance, and pushed through a pinhole projection, the one line of maths behind every camera, size on screen equals size over distance. Now the test knows every answer before asking, because it chose the answers.
The generator's own tests read like physics homework: the iris at half a metre must span exactly 11.7 over 500 of the frame, doubling the distance must exactly halve it, and the EAR of a synthetic face must equal aperture over eye width to ten decimals, three increments shaking hands.
Note the conventions block at the top of the file, axes, rotation order, signs, written once. Convention bugs are the worst bugs in geometry because every formula is locally right and the whole is wrong.
Synthetic answers keys and recorded reality now work as a pair, exactly as 2.7 planned: the generator grades the maths, your fixture confronts it with noise. Every increment through 3.8 tests against this generator, starting immediately with 3.4's millimetres.

## 3.4 Dividing by the ruler you were born with

The concept this increment teaches is unit conversion by reference object, the trick that turns a camera into a measuring instrument.
A camera reports pixels, and pixels are a lie about size: lean 20 centimetres closer and your eye doubles on screen without opening at all. Absolute measurement needs something in frame whose true size is known. Photographers put a ruler beside the evidence. We are luckier, every face carries one: the visible iris is within a few percent of 11.7 millimetres across in nearly all adults. So each frame, we ask how many pixels the iris spans, and that gives the price of a millimetre in this frame, at this distance, refreshed sixty times a second. The aperture in pixels divided by that price is the aperture in millimetres, and the flagship test proves the payoff: across synthetic faces from 350 to 800 millimetres away, the pixel number swings past double while the millimetre number does not move in the tenth decimal.
Two craft notes. The ruler is the horizontal iris diameter, because the vertical one hides behind the lids exactly when blinks make measurement interesting. And the aspect ratio trap: normalised x is a fraction of frame width, normalised y of frame height, on a 16:9 frame those units differ by almost double, so everything becomes pixels before directions mix. Mixing them raw would skew every millimetre by that factor, silently.
Reality graded the work too: the median across your 300 recorded frames came out at 7.1 millimetres, with mid blink dipping to 2.5. Plausible human numbers, from arithmetic and one anatomical constant.
This number becomes the blink signal of Phase 4, gets distance validated at 3.5, and tilt corrected at 3.7.

## 3.5 One fair number for wobble

The concept this increment teaches is the coefficient of variation, and behind it, how to compare variability fairly.
The question was: does the millimetre aperture really hold steadier than the pixel one when you move? Raw standard deviations cannot answer it, a deviation of 3 pixels and a deviation of 0.3 millimetres are in different currencies, comparing them is meaningless. The exchange rate is the mean: divide each deviation by its own average and both become unit free percentages of themselves. That ratio is the coefficient of variation, CV, and it lets pixels and millimetres stand on one scale.
The verdict is now a permanent test: sweeping synthetic faces from 350 to 800 millimetres, the pixel aperture's CV exceeds 25 percent while the millimetre CV stays under a tenth of a percent. On perfect synthetic data the ruler cancels distance exactly, real faces will be noisier, which is why the live stability line exists: perform the lean in, lean out experiment yourself and watch the two percentages diverge on screen.
One honesty guard: CV divides by the mean, and a mean near zero, eyes long closed, makes the ratio explode into nonsense. A mean at or below zero returns null, the refusal rule again.
CV returns in the analysis track at Phase 7, where every claimed result will carry a variability alongside its average, and the stability line becomes demo material for the pixels versus millimetres story, the strongest post of the ladder.

## 3.6 Three named angles out of one matrix

The concept this increment teaches is rotation as a matrix, and Euler angles as its human readable unpacking.
The model does not only report landmarks, it also reports how the whole face is turned, as a 4 by 4 transformation matrix, sixteen numbers encoding rotation and position at once. Machines love that form, you can chain and invert it, but no human reads sixteen numbers. The human form is three named angles: pitch (nodding), yaw (shaking no) and roll (ear to shoulder). The decomposition in core recovers them from specific matrix cells, and the convention block matters more than the formulas: which axis is which, in what order rotations compose, matching the synthetic generator exactly.
Two things worth keeping. First, the tests build their matrices by multiplying base rotations numerically, an independent code path from the decomposition, so the test genuinely inverts rather than echoes. Second, gimbal lock is real: pitch the head a full 90 degrees and yaw and roll collapse into one indistinguishable axis, so the decomposition returns null there, the refusal rule in its most geometric costume.
One honest asterisk: our convention is proven against our own synthetic matrices, but MediaPipe's real matrix may order axes or flip signs differently. The nod, shake, tilt manual check is the calibration experiment, and the observed signs get recorded for 3.7 and 3.8.
Pose feeds the validity gate at 3.8 directly: measurements will refuse to exist when the head turns too far, using exactly these three numbers.

## 3.7 The correction we never had to write

The concept this increment teaches is invariance by construction, the quiet superpower of choosing the right representation early.
The master plan scheduled a roll correction here, expecting the aperture to shrink when the head tilts, as it does in most implementations. Ours does not, and the reason is a decision made back at 3.1 without fanfare: we measure the straight line distance between two landmarks, not the vertical drop between them. Rotation moves points around, but it cannot stretch the space between them, so a distance based measurement is immune to roll before any correcting code exists. Your ritual prediction caught this, and your 42 degree tilt screenshot confirmed it live before the tests did.
The increment therefore delivers proof instead of a patch: the ladder's 0, 15, 30 sweep shows the millimetre value frozen to ten decimals, and a counterfactual test implements the naive vertical measurement locally just to document its failure, shrinking by exactly cos(roll), 13 percent at 30 degrees. The bug we never wrote now lives in the test suite as a warning to whoever changes the aperture code later.
The wider lesson: corrections undo errors after the fact, representations can make the error inexpressible. When you get to choose, choose the representation. The same idea already carried EAR through distance changes (a ratio cannot see scale) and returns at 5.6, where the question will be which gaze representation makes head wobble cheapest to survive.
Roadmap amendment 4 records the change honestly: the plan said correction, the geometry said verification.

## 3.8 A measurement with preconditions

The concept this increment closes Phase 3 with is the validity gate, the idea that a serious measurement knows the conditions under which it deserves belief, and says so.
Every number this phase built rests on assumptions: the eye landmarks are visible, not foreshortened into slivers, not occluded by the nose. Turn your head 40 degrees and those assumptions quietly die, but the arithmetic keeps producing numbers, wrong ones, wearing the same font as the right ones. The gate makes the assumptions executable: pitch, yaw and roll are checked against limits every frame, and beyond them, EAR and aperture become "no valid measurement", the sparkline records a gap, and one sentence names the axis, the angle and the limit. The head pose line keeps working, deliberately, so you can steer back into validity.
Design details that matter: the limits are symmetric, so the sign conventions we never fully calibrated cannot matter to the gate. The boundary is inclusive, exactly at the limit is still valid, and the tests check below, at and above, our oldest threshold rule. An unknown pose gates as invalid too, unknown is not a licence.
This is the pattern the whole project has been converging on: 1.2 refused broken cameras, 2.5 refused wrong models, 4.6 will refuse low frame rates, and now geometry refuses untrustworthy angles. An instrument that cannot say "I do not know" is not an instrument, it is an opinion generator.
Phase 3 ends here: pixels became millimetres, the head learned its angles, and every number learned when to stay silent.

## 4.1 The threshold is a decision, not a fact

The concept that opens Phase 4 is event detection, turning a continuous signal into countable happenings, and the confession at its heart: every event detector hides a decision.
The detector itself is three states and one rule. The aperture runs below 4 millimetres, the eye counts as closed; it rises back, one blink is counted, on the reopen, so a held closure counts once when it ends. An invalid frame, face lost or head turned too far, breaks the cycle: a blink we could not watch from start to finish is not a blink we may count, the gate's honesty flowing downstream.
The decision is the 4. Your own fixture priced it: your full blinks bottom near 2.2 millimetres, your shallow half blink near 5, your open eyes near 7. Any threshold from 3 to 4.5 finds exactly two blinks, at 5 the third appears. So "how many times did you blink" has no answer independent of a chosen line, and the tests now document both answers with their prices. This is the ritual's mystery from 3.1, resolved into arithmetic.
Two blindnesses ship on purpose, each with its increment booked: the threshold is tuned to one person's anatomy, 4.2 learns it per person instead, and a slow deep squint will fool it, 4.7 separates them by shape.
Everything else in Phase 4 decorates this reducer: durations at 4.3 are time between its transitions, rates at 4.4 count its events per minute, velocities at 4.5 measure how fast the signal falls into it.

## 4.2 A bar that only rises

The concept this increment teaches is adaptive calibration with a ratchet, and the quietly adversarial reasoning behind it.
The 4 millimetre threshold was tuned to one person on one day. Now the instrument learns instead: thirty seconds of watching, and the threshold becomes half of what YOUR open eyes measure. The robust part is which statistic defines "open": a plain mean would let every blink inside the learning window drag the estimate down, so the baseline is the 90th percentile, the level your lids are above nine tenths of the time, which shrugs off brief closures.
The adversarial part is the ratchet, and it is the ladder's own named test: after learning, the baseline may rise but never fall. Why one way only? Because the very thing later phases exist to notice, lids drooping with fatigue, looks exactly like "this person's eyes are just narrower, adapt to it". A two way adaptive baseline would learn the drowsiness away, lowering the bar precisely when the bar matters. The ratchet makes that impossible: wider than ever, believed; narrower for minutes, treated as a finding, not a recalibration.
The ratchet costs something too, honesty requires saying it: a genuine context change that narrows the eyes, moving the screen higher, say, would leave the baseline stuck high. The escape is explicit: restarting the camera restarts the learning, a human decision, not an automatic one.
The baseline returns immediately at 4.6 and 4.7 as the reference the honesty gates lean on, and at 6.5, where "how open compared to YOUR normal" feeds the score.

## 4.3 A blink gets a clock

The concept this increment teaches is the event with extent: a blink stops being a tick on a counter and becomes a stretch of time with a beginning and an end.
The mechanics are small. The reducer already knew the moment the eye closed and the moment it reopened, it merely never wrote down the clock. Now it does: the closing timestamp is remembered, and the reopen reports the difference, the closed phase duration in milliseconds. An invalid frame still voids everything, including the pending timestamp, an unfinished measurement is not a measurement.
The definition deserves one honest sentence: our duration is the time spent BELOW the threshold, the closed phase, not the full lid journey from descent to fully reopened that some papers mean by blink duration. Definitions vary across the literature, ours is written down, which is what matters.
Why duration earns its place in a fatigue instrument: sleepy blinks are longer. The closed phase stretches measurably as drowsiness grows, which makes this number, unlike the raw count, a direct fatigue signal, the first one blinklab produces.
The owner's own data calibrated the tests: the two recorded blinks measure 133 and 117 milliseconds below threshold, textbook values for alert spontaneous blinks, now pinned as assertions. When a fatigue dataset arrives in Phase 7, longer numbers than these are part of what the classifier will look for.
Duration is the second column of the blink event log at 4.8, and the velocity work at 4.5 dissects this same stretch of time into its falling and rising halves.

## 4.4 Rates and the young window problem

The concept this increment teaches is the rolling rate, and its classic trap, the window that has not lived long enough to be believed.
A rate is events divided by time, and both halves need care. The events half is familiar machinery: blink timestamps pruned by the same keepRecent that has served the fps counter since 1.3, the oldest falling out as the window slides. The time half is where honesty lives. Divide by the full sixty seconds when you have only observed five, and a normal person reads as nearly blinkless. Divide by five seconds naively, and one blink reads as twelve per minute of confidence built on nothing. So the denominator is the time actually observed, capped at the window, and below fifteen seconds of observation there is no rate at all, only "measuring...", the refusal rule applied to arithmetic that would technically compute.
Why the rate matters: it is the most famous number in blink research. At rest most people sit near fifteen to twenty per minute. Concentration crushes it, screen reading famously drops it by half or more, which is why dry eyes follow long reading sessions. Drowsiness tends to raise it, alongside the lengthening durations from 4.3. Rate and duration moving together is exactly the pattern the Phase 6 score will watch for.
The rolling window itself returns at 6.1 as PERCLOS's backbone, where the same sliding sixty seconds measures not how often the eyes close but how long they stay that way.

## 4.5 The shape is where the information is

The concept this increment delivers is the phase's thesis: a blink is not a binary event, it is a movement with a profile, and the profile carries what the count cannot.
Three numbers describe the profile. Amplitude, how far the lid fell, from its pre closure maximum to the minimum. Peak closing velocity, the fastest adjacent sample drop on the way down, in millimetres per second, deliberately per second so a frame rate change cannot silently rescale it, the tests use uneven timestamps to enforce exactly that. And their ratio, amplitude over velocity, a time constant measured in milliseconds.
The ratio is the clever one, and it comes from the drowsiness literature: as people tire, lid velocity fades before lid travel does. A tired blink falls about as far but noticeably slower, so amplitude over velocity stretches. It is also naturally self normalising, sharing the same ruler in numerator and denominator, echoes of the EAR's trick.
The extraction respects its own limits: it measures the descent only, from the pre closure maximum, ignoring whatever the window starts with and the reopening tail, and it refuses degenerate input, too few samples, no fall, or a clock that did not advance.
The manual check is the demonstration the whole phase was named for: a natural blink and a deliberate slow one have similar amplitudes and utterly different velocities, and the page now shows that difference in numbers.
These three numbers join duration and rate in 4.8's event log, and the score at 6.5 will weigh the ratio among its inputs.

## 4.6 Zero is a claim, null is an admission

The concept this increment teaches is the sampling limit, and the master plan's own words for it: the detector now refuses to answer when it cannot see properly.
The physics is short. A quick blink's closed phase can be under 100 milliseconds. At 60 fps that phase spans six frames, comfortably visible. At 20 fps it spans two at best, and with slight mistiming, zero, the eye closes and reopens entirely between samples. The detector would then report few blinks with total confidence, and a false calm is worse than no reading, because low blink counts are exactly what a fatigue system treats as meaningful.
So below 25 fps, every temporal blink metric returns null and the page says not measurable, naming the current rate and the minimum. The ladder's test spells out the distinction the whole increment turns on: with real blinks sitting in the window, the gated rate below 25 fps must be null and must NOT be zero. Zero says "this person did not blink", null says "I could not have seen it either way". One is a claim, the other an admission, and instruments that cannot tell them apart produce confident nonsense at their edges.
This is the fourth refusal in the family: broken cameras at 1.2, wrong models at 2.5, turned heads at 3.8, and now starved sampling. One honest simplification is on record: the rate's observation clock keeps running through a low fps spell, mildly diluting the rate afterwards, accepted rather than hidden.
The gate feeds 7.8's latency measurements, where sampling limits get quantified rather than just respected.

## 4.7 Not everything that dips is a blink

The concept this increment teaches is classification by time signature: two events can cross the same threshold and still be different things, told apart by how long they stay.
A blink and a deep squint both drive the aperture below the line. The difference is temporal: your recorded blinks spent 133 and 117 milliseconds down there, while a held squint parks for seconds. So the rule is one comparison: a closure only counts as a blink if it lasted half a second or less below threshold. The ladder's synthetic five second plateau now counts exactly nothing, and the sparkline session where you watched your own squint draw a plateau instead of a valley was this rule's preview, shape first, code later.
Two honest notes. First, 500 milliseconds is another decision line, like 4.1's four millimetres: real blinks and real holds separate widely around it, but the line itself is chosen, documented, and boundary tested, exactly at 500 counts, 600 does not. Second, this increment reclassifies old behaviour: 4.3's manual item promised a held two second blink would read 2000 milliseconds, and that promise is now amended, a two second closure is not a blink, it is a long closure, which increment 6.2 will detect as its own event with its own name. Definitions evolving in the open, with the paper trail updated.
The taxonomy this begins, brief blink versus long closure versus sustained droop, is the backbone of Phase 6: PERCLOS measures the droop, 6.2 catches the closures, and the blink metrics stay clean of both.

## 4.8 From readings to records

The concept that closes Phase 4 is the event log, the difference between an instrument you watch and an instrument that remembers.
Every line on the page until now was a reading: true at this instant, gone the next frame. The log makes blinks durable: each completed one becomes an event carrying when it ended, how long it stayed closed, and its shape, appended to a capped list that the panel renders newest first. The reducer is the shared ring buffer's third posting, after the timing samples and the sparkline, push forever, memory fixed, oldest fall away, and the cap's silence is documented rather than hidden, fifty events, then history starts eating its tail.
Formatting is a pure function too, which looks fussy until you notice what it buys: the exact text of a log line, relative seconds, units, the "shape unavailable" fallback, is unit tested, so the panel cannot silently drift from its contract.
The log is also Phase 6's rehearsal. The session recorder at 6.7 is this same idea grown up, every FeatureRecord instead of every blink, exported as CSV instead of rendered as a list. And the log answers a question every fatigue system eventually faces: not "is this person blinking oddly now" but "when did it start", which only a record can answer.
Phase 4 ends here: a counter that learned whose eyes it watches, when it cannot see, what does not count, and now, how to remember.

## 5.1 Gaze begins as a projection

The concept that opens Phase 5 is measuring within a moving frame of reference, done here with the oldest tool in geometry, the projection.
The raw gaze signal is simply where the iris centre sits inside its eye. But "inside its eye" is a moving target: the eye slides around the image with every head shift and rotates with every tilt. The fix is to measure in the eye's own coordinate system: the axis between the two eye corners becomes the ruler and the direction at once, the iris position is projected onto that axis for the horizontal offset and onto its perpendicular for the vertical, both expressed as fractions of the eye width. Head roll then rotates the ruler and the signal together and cancels out, the same invariance-by-construction that saved 3.7, now proven for gaze by a test that rolls the synthetic face 15 degrees and demands identical offsets to eight decimals.
The synthetic generator grew a gaze of its own for the occasion: an iris shift parameter, so the tests know the truth in millimetres, a 3 mm shift on a 30 mm eye must read exactly 0.1.
Convention, stated once more because Phase 5 lives or dies by it: horizontal positive toward image right, vertical positive toward image bottom, in unmirrored measurement space. The manual check asks the owner to observe which direction of real gaze reads positive, the calibration note 5.2's quadrant mapping will consume.
Everything in this phase builds on these two numbers: quadrants at 5.2, calibration at 5.4, fixations at 5.7, the heatmap at 5.9.

## 5.2 The first classification, and the mirror inside the signs

The concept this increment teaches is classification, turning continuous numbers into a named answer, and the perspective flip hiding inside it.
The mechanics are two comparisons: the mean of both eyes' offsets, split at zero on each axis, gives one of four quadrant names. The intelligence is entirely in the signs, and they contain a genuine surprise worth working through once. When you look toward YOUR screen's left, your irises rotate toward your own left, and in the unmirrored camera image your left side appears on the RIGHT. So positive horizontal, image right, means screen left. The measurement space and the user's perspective are mirror images of each other, and the quadrant names are spoken in the user's language, which is the only language a "Looking toward" line should speak.
The labelled fixtures the ladder asked for are synthetic: each gaze shift carries the quadrant a human at the screen would name, and the classifier must agree on all of them, both axes, both magnitudes.
Two honest limits ship in the open. Zero-centred boundaries assume neutral gaze reads zero, which no real setup guarantees, a laptop camera above the screen makes "straight ahead" read slightly downward, biasing the vertical split. And averaging both eyes trusts them equally. Both limits are calibration's business, and calibration is 5.4, two increments away, which is exactly why the display says "uncalibrated" after its answer.
Classification returns immediately at 5.3, where the question becomes binary, on screen or off, and the honest answer needs a threshold rather than a sign.

## 5.3 The attention boundary

The concept this increment teaches is the difference between direction and presence: quadrants ask where on the screen, this asks whether the screen at all.
The rule is a box: if either offset axis exceeds the threshold, the gaze has left the screen and no quadrant applies, the line says off screen instead. Either axis, not both, one glance sideways is enough to be gone. The threshold, 0.18 of an eye width, was priced by the owner's own observation at item 30: corner glances swing 0.05 to 0.15, so the boundary sits above every on screen glance and below any real look away, another decision line with its boundary trio, exactly at counts as on.
The quiet importance: this is the project's first attention measurement. Blink metrics say how the eyes are, gaze quadrants say where they point, but on screen versus off is the primitive behind every "was the user even engaged" question, screen time, distraction counting, the attention share of the eventual score. Phase 5's remaining rungs sharpen it, calibration replaces the guessed threshold, and fixations at 5.7 tell absorbed stillness from vacant staring.
It also composes with everything before it: the pose gate already catches the turned HEAD, this catches wandering EYES under a still head, two different escapes from the screen, refused by two different gates, each naming its own reason.

## 5.4a Ground truth, manufactured on demand

The concept this increment teaches is supervised data collection, the deliberate manufacture of labelled examples, and the discipline of collecting them honestly.
Calibration will need pairs: "the gaze offset measured THIS is where the eyes pointed at THAT". Reality never volunteers such pairs, so we stage them. A dot appears at a known viewport position, the person looks at it, and for that moment the label is certain. Nine dots, thirty trusted samples each, and 5.4b's solver will have 270 labelled examples to learn this person's mapping from.
The honesty is in what the collector refuses. Nothing counts during the settle window after a dot moves, because sampled mid travel the eye is demonstrably NOT looking at the target yet, those samples would carry confident wrong labels, the worst kind of data. Invalid frames, blinks, turned head, lost face, never count either, they just make a dot's stay longer. The reducer that enforces all this is pure and tested to its boundaries: exactly the quota advances, one less does not.
Two design notes. The samples persist in this browser's local storage and nowhere else, the privacy stance extended to derived data. And cancellation is one click, staged data collection should always be escapable.
This is also the project's first taste of what Phase 7 does at scale: datasets are just this ritual performed by many people, and the same poisons, mislabelled moments, travel time, sneak into them the same way.

## 5.4b The first learned parameters

The concept this increment teaches is fitting: turning labelled examples into a model, done here with the smallest model that could possibly work, one straight line per axis, four numbers in total.
The pipeline is two honest steps. Each dot's thirty samples collapse to their MEDIAN offset, the robust middle, because a median barely moves when one wild sample sneaks in where a mean would be dragged a full unit, and the test proves exactly that with a planted outlier. Then ordinary least squares fits a line from the nine medians to the nine known screen positions: the slope and intercept that minimize the squared misses. That is the entire solver, readable in one sitting, which is the point, explainability beats accuracy whenever they compete.
Two things the profile learns without being told. The mirror flip that 5.2 hand-derived, positive offset means screen left, arrives as a NEGATIVE slope, discovered from the data. And the camera-above bias that made "straight ahead" read downward vanishes into the intercept, the load-bearing test stages that exact bias, shows the zero-split classifier calling both top corners "bottom", and demands the calibrated classifier get them right from the same samples.
The refusal family grows a solver branch: an empty capture, a single dot, a frozen iris with no spread, an axis that never varied, all return null rather than a confident wrong line. A profile that could answer only one axis is no profile.
This is also the project's first supervised learning, in miniature and fully transparent: 5.4a manufactured the labelled data, 5.4b fit the parameters, and the stored profile is a personal model of one face's geometry. Phase 7 does the same thing at scale with a classifier, and every honesty rule rehearsed here, robust summaries, refusing degenerate fits, applies unchanged there.

## 5.5 The test pyramid grows its top

The concept this increment teaches is the test pyramid, and why the top layer exists at all. Two hundred and seven unit tests prove every part: the capture reducer refuses mid travel samples, the solver refuses a frozen axis. Not one of them proves the ASSEMBLY, that clicking the button reaches the reducer, that the reducer's target index reaches the dot on screen. A part can be perfect and the wiring between parts still broken, and until today no test would have noticed.
An end to end test drives the assembled thing: a real browser loads the real production build, clicks the real buttons, and asserts what a person would see. That breadth is expensive, the single journey test costs about five seconds while all 207 unit tests together cost about one, which is the pyramid's whole argument: many fast narrow tests at the bottom, a few slow broad ones at the top, never the other way round.
The camera problem had a two flag answer: Chromium can fake a video device and auto grant permission, so the flow runs headlessly on a machine with no camera at all. But the fake stream carries no face, and that line is worth respecting rather than fighting: the end to end test proves wiring, the overlay opens on dot 1 of 9, one click cancels, a cancelled run stores no profile. It never proves vision. The math already has its unit tests, and the face still needs the owner's own, per MANUAL.
One small idea rode along: the test grips the page by `data-testid` names, not by styles or copy. ## 5.6 The jitter-lag tradeoff, escaped by adapting

The concept this increment teaches is the jitter-lag tradeoff, the oldest dilemma in signal filtering, and the trick that escapes it: let the smoothing strength follow the speed.
Every smoothing filter is a compromise between two failures. Smooth hard and the jitter dies, but a real glance arrives late, smeared over half a second. Smooth lightly and the glance stays crisp, but so does every trembling pixel. A fixed-strength filter must pick one failure and live with it. The One Euro filter (Casiez, Roussel and Vogel, 2012) refuses the choice: it estimates how fast the signal is moving, and sets the smoothing from that. Still eye, strong smoothing, jitter gone. Moving eye, light smoothing, the step lands almost as fast as the raw signal. Every piece is an exponential moving average, and the adaptation itself is one linear rule, readable in a sitting.
The ladder's check made the tradeoff measurable. After a step, the smoothed value must cover 90 percent of the jump within 150 milliseconds: the adaptive filter covers 97 percent while cutting jitter to a third. The counterfactual, in 3.7's tradition: a fixed filter built for the same jitter reduction covers only 53 percent in the same budget. That 44 point gap is the entire argument for adapting.
The 3.7 entry promised a question would return here: which gaze representation makes head wobble cheapest to survive. The answer is that the filter never meets head wobble at all. It smooths the corner-axis offset, a representation where roll and distance are already invisible by construction. Smoothed raw pixel positions would have forced the filter to choose between blurring head motion and following it, one more time the representation eats a problem before the code has to.
One honest limit, visible on the vertical trace: the filter preserves blinks. A blink drags the iris estimate downward fast, and fast is exactly what this filter is built to follow. Smoothing removes noise, not events. Telling deliberate eye movements from artifacts is classification, not filtering, and that is 5.7's business.

## 5.7 The eye does not glide

The concept this increment teaches is that gaze is not a continuous stream, it is a sequence of discrete events. The eye parks on a spot, holds nearly still for a few hundred milliseconds (a fixation), then jumps to the next spot in a movement too fast to see during (a saccade). Almost everything the mind takes in arrives during the parks. Reading, searching, watching: all of it is hop, park, hop.
The separator is I-DT, identification by dispersion threshold (Salvucci and Goldberg, 2000), and it needs exactly two thresholds, one in space and one in time. Dispersion is how far a stretch of gaze spreads, horizontal range plus vertical range. A fixation is any stretch that stays inside a small dispersion box for at least a minimum duration. Seed a window spanning the minimum, check the box, extend while it still fits, record start, end and centroid, continue after. Everything the windows reject is movement. The whole algorithm is one loop, readable in a sitting.
This is the third time the project has classified by thresholds, and the pattern is now worth naming. 4.1 used one line in space (aperture below 4 mm). 4.7 added one line in time (closed half a second or less). 5.7 needs both at once: still enough, for long enough. Two-threshold classification is the workhorse of event detection, and every threshold keeps the house rules: named constant, documented choice, boundary tested on all sides, exactly at the line still counts.
The detector is also 5.6's first customer, and the dependency is load-bearing. Raw gaze jitter spreads roughly as far as the dispersion box itself, so raw input would shatter every real fixation into fragments. The smoothed signal spends its stillness well inside the box. Filters exist for their consumers, and this is the first proof.
One honesty rule carried over: fixations never bridge gaps. A lost face or a refused head pose clears the buffer, because a fixation stitched across missing frames would be an invented stillness. And the two-threshold rule quietly explains the display's behaviour: after every jump the line reads "moving" for the first 120 milliseconds of the new stillness, because stillness is not a fixation until it has lasted. The statistics over these events, how long, how many, where, are 5.8's business.

## 5.8 From events to a distribution

The concept this increment teaches is aggregation: the step from "things happened" to "here is their shape". 5.7 made fixations into events with a start, an end and a place. Alone, each event says almost nothing. Summarized, they become a signature: many short fixations is what reading looks like, few long ones is what staring looks like, and the difference shows up in four numbers before any scanpath is drawn.
The panel reports count, mean, median and longest over the rolling 10 second window, and every number rides on machinery that already existed: mean from 3.5's statistics, median as the nearest rank 50th percentile from 4.2's percentile, the same convention 5.4b used to collapse calibration samples. Nothing new was invented, which is the quiet point: once small tested pieces exist, new increments become composition, and composition is cheap.
Mean and median travel together on purpose. For clean fixations they nearly agree, but one abnormally long fixation drags the mean while the median barely moves, the same robustness argument that made 5.4b choose medians. When the two numbers disagree, the disagreement itself is information: something unusual sits in the window.
One design choice worth recording: the still-growing current fixation counts at its length so far. A panel that waits for a fixation to end would sit stale through every long stare, exactly the moments worth watching. The cost is honesty about drift: the longest number can climb live as you stare, which is not a bug, it is the measurement keeping up.
These four numbers are also Phase 6 material in rehearsal: fixation statistics are classic features in the attention and drowsiness literature, and the FeatureRecord at 6.4 will want exactly this kind of windowed summary, one row per second.

## 5.9 Dwell, binned

The concept this increment teaches is accumulation by binning: turning a stream of continuous positions into a picture, by dividing space into cells and counting time spent in each.
The heatmap is the simplest possible memory of attention. Every trusted frame, the calibrated gaze point falls into one cell of a 16 by 9 grid, and that cell counts one frame of dwell. No decay, no blur kernel, no cleverness: a count per cell, normalized so the hottest cell is exactly one, drawn as transparency. Where you looked longest glows brightest, arithmetic anyone can audit.
Binning has one sharp edge, literally: the boundary. A fraction of exactly 1.0 is still the screen's far edge, so it clamps into the last cell rather than indexing off the grid, while 1.001 is off screen and accumulates nowhere. The same exactly-at-the-line discipline as every threshold before it, tested from both sides.
Two design choices carry the project's values. The grid is deliberately coarse because amendment 2 set the calibration target at quadrant level reliability: a fine grid would render precision the profile does not have, and a blob spread over neighbouring cells is the honest picture of a linear fit's error. And the heatmap is the calibrated profile's first live consumer beyond a label: raw offsets have no screen meaning, only calibratedPoint places gaze on the screen, which is why the button waits for a profile.
The test card is drawn, not photographed: five shapes at known screen fractions, so you know the ground truth of where you looked, and no image licence rides along in a public repo.
What is missing is time. The heatmap says where attention pooled but not in what order, and order is what distinguishes reading from searching from wandering. Order is 5.10's business, the scanpath replay, the last rung of Phase 5.

## 5.10 Time on a slider

The concept that closes Phase 5 is replay: once events are recorded with timestamps, time stops being something that happens to you and becomes an axis you can hold in your hand.
The machinery is one question asked fast. The slider picks a moment, and the recording must answer: how much of the path existed by then? With samples stored in time order, the answer is a binary search, the first true algorithm of the classics to appear in this codebase. Instead of walking all samples counting, it halves the search space each probe: a five minute recording of eighteen thousand samples answers in about fifteen comparisons instead of eighteen thousand. The test pins the search against the obvious slow count at every kind of probe, which is the standard way to trust a fast algorithm: prove it agrees with the dumb one.
The drawing on top is composition, nothing new: the travelled path is the sparkline's polyline, the fixation circles are the 5.7 detector rerun on screen points with a screen sized dispersion box passed explicitly (the detector never cared what its two numbers meant, only that they were positions), and their radius encodes duration, the parks drawn bigger the longer they held.
Heatmap and scanpath are the two halves of one truth, and now both exist: 5.9 shows where attention pooled, 5.10 shows in what order it travelled. Pooling without order cannot tell reading from staring at a word; order without pooling cannot tell a glance from a dwell. Every eye tracking paper you will ever skim shows both figures side by side, and now both come from functions you can read.
Phase 5 ends here: gaze measured in the eye's own frame, classified into quadrants, bounded on screen, calibrated to one person, smoothed without lag, split into fixations and saccades, summarized, pooled, and finally replayed.

## 6.1 The duty cycle of the eyelid

The concept that opens Phase 6 is the duty cycle: measuring not whether something happens, but what share of time a system spends in a state. Phase 4 counted blink events. PERCLOS asks a different question about the same eyelid: across the last minute, what fraction of the time was it down? An awake eye closes often but briefly, a few percent of any minute. A drowsy eyelid does not only blink differently, it sags and lingers, and lingering is invisible to an event counter while a duty cycle cannot miss it. That is why PERCLOS, of all the eye measures, is the one with decades of validation behind it.
The mechanics compose three earlier increments without inventing anything. Closed means at or below 20 percent of YOUR open baseline, the classic P80 convention priced against 4.2's personal ratchet, because absolute apertures differ between faces (the wink observation from 3.1 taught this early). The window follows 4.4's observed-time discipline, no number until 15 seconds of valid reality sit in it. Untrusted frames, gate refusals, lost faces, low fps, join neither side of the ratio, the same gaps-are-gaps rule every window here has kept.
One honest choice worth naming: classification happens at push time, against the baseline of that moment, so when the ratchet later raises the baseline it never rewrites history. A sample is the verdict of its own instant. The alternative, reclassifying the past every time the threshold improves, sounds more accurate and is actually a lie, because the past was measured with the knowledge of the past.
The ratio is sample weighted rather than time integrated, which equals time weighted at a steady frame rate, and the fps gate upstream already refuses the unsteady case. Written down, tested at the boundary, moving on.
6.2 takes the complementary question: not the share of closed time, but the single closure that goes on too long.

## 6.2 The event that fires while it is still happening

The concept this increment teaches is the difference between detecting an event after it ends and detecting it while it is underway, and why safety-shaped signals must do the second.
Every event so far was reported at its end. A blink counts on the reopen, a fixation exists once the window closes behind it. That is the honest default: you know what a thing was once you have seen all of it. But a long closure is the one event in this project whose whole point is that it might still be going on. Eyes shut for two seconds matter BECAUSE they are still shut. A detector that waits for the reopen to speak would file a report about the microsleep after the driver woke up. So this reducer fires the moment a closed frame crosses the line, mid event, and the reopen normally only fills in the final duration.
One exception exists, and it was found by adversarial review before this ever merged, which is worth recording as a lesson of its own. A camera samples: frames land every 33 milliseconds or so, and a closure can cross the line BETWEEN its last closed frame and the reopen frame. The blink reducer measures the span at the reopen and refuses anything beyond the maximum, but the first draft of this detector only fired on closed frames, so a fully witnessed 510 millisecond closure could land in neither bin, a hole about one frame wide sitting exactly on the boundary. The fix fires late, on the reopen, using the same reopen-measured span the blink reducer uses to refuse it, and a new test now runs BOTH reducers over one stream of frames and demands that every closure lands in exactly one bin. Sampled time is not continuous time: any rule written as "when the value crosses the line" must decide what happens when the crossing falls between two looks.
The line itself is borrowed, not invented: it is the blink maximum from 4.7, aliased so the two detectors share one constant. At or below it, the closure is a blink and blink.ts counts it. Strictly beyond it, it is a long closure and this counts it. Every closure lands in exactly one bin, and no future edit can split the definitions apart without the equality test noticing. 4.7's taxonomy, brief blink versus long closure versus sustained droop, now has its second member built, and PERCLOS already watches the third.
One firing per closure, however long it holds: the fired flag is the debounce inside the event, and 6.3 adds the debounce between events, so an alert cannot nag. The unwitnessed cases keep their honesty rules: a face lost before the line means no event (frames nobody saw prove nothing), a face lost after the firing keeps the count (that moment was witnessed) but records no duration (the end was not).

## 6.3 An alarm's first duty is restraint

The concept this increment teaches is debouncing, and behind it a human one: alarm fatigue. An alarm that fires on every trigger nags, and a nagging alarm trains its owner to ignore it. Hospitals learned this the hard way, monitor alarms dismissed by reflex, and cockpit design learned it before them. The fix is not a better sound, it is restraint: after one firing, hold your tongue for a window, however many triggers arrive.
The governor is a small pure reducer with one decision per frame: may this trigger fire? Yes if no firing happened within the last five seconds, otherwise the trigger is swallowed. Two details carry the honesty. Swallowed triggers are counted, not silently eaten, so the banner says "suppressed: 2" and the record stays complete. And the window is measured from the last FIRING, never from a suppressed trigger, because the alternative re-arms the clock on every swallow and a fast enough stream of triggers would silence the alert forever, the exact opposite of its job.
The taxonomy of restraint is now three layers deep, worth seeing as one design. The fired flag inside 6.2 debounces within one event: one closure, one count. This window debounces between events: one firing per five seconds. And the display window is a third quiet timer: the banner shows for three seconds and leaves, because a page that shouts permanently is a page nobody reads. Three timers, three named constants, each boundary-tested on all sides, exactly at the line still counts.
This is also the project's whole alert stack finished in miniature: detector (6.2) to governor (6.3) to display, each a pure function, each tested alone. The score at 6.5 will reuse the same separation, compute, then govern, then show.

## Amendment 5: the instrument's zero is not the world's zero

The concept this fix teaches cost a wrong prediction to learn, which is the best kind: a decision line is only meaningful inside the range the instrument actually produces, and that range must be measured, never assumed.
The plan looked clean on paper. The literature's PERCLOS convention calls an eye closed below 20 percent of its open baseline, our long closure detector would simply adopt that line, and the owner's false alarms, caused by naturally low eyelids reading at the bottom of a screen, would vanish. The prediction on record said their PERCLOS would jump to roughly ten percent during a six second closure. The measurement said 0.0 percent, through a fully witnessed thirteen second closure. The 20 percent line was not strict, it was UNREACHABLE: the landmark model, watching this face through strong glasses, reports fully shut eyes as about a third of baseline. The literature's convention silently assumes an instrument whose shut reading is near zero. Ours has a floor, and the floor sits above the line.
So the shut line was priced from measurements instead: the owner's shut floor near 33 percent, their relaxed reading droop at 45 to 50 percent, the line at 40, the midpoint, both margins written down. One word, closed, turned out to hide three physical states, the rapid descent of a blink, the relaxed partial droop of a low lid, and eyes actually shut, and each consumer now names which one it watches. The band between the blink line and the shut line is a partial droop, deliberately no event at all.
Two meta lessons ride along. The bug announced itself as a DISAGREEMENT between two measures, long closures counting seconds while PERCLOS read zero on the same frames: redundant measurements that should agree are a bug detector nothing else replaces. And the fix was decided by a thirty second experiment performed before a line of code was written, which is the cheapest debugging there is. PERCLOS itself still carries the unreachable line, on record as its own issue, so the instrument's honesty debt is filed, not forgotten.

One postscript, because the review of this fix earned it. Twenty one agents attacked the 40 percent line before it shipped and confirmed twelve findings, three of which reshaped the fix. The ratchet, which never lowers the baseline, would have pushed a live shut line above the measured droop after two seconds of widened eyes, so the shut line now freezes at each session's first learned baseline. The regression test's droop was scripted at 3.7 mm, which sits above the OLD line too, so the test could not actually fail against the old wiring, the exact mistake a regression test exists to prevent, now fixed with a value inside the measured band and bracket probes at the measured edges. And the two-line design has a documented cost: a slow descent spends time in the droop band before reaching shut, and that time does not count yet, so alerts trail true onset, on record as the next redesign. A fix that survives adversarial review is not the fix you started with, and that is the point of the review.

## Fix #114: the design that died in review, and the one that shipped

The concept this fix teaches arrived in two acts, and the first act failing is most of the lesson.
The problem: one line plus noise mints events. The owner's log filled with seventeen millisecond, zero point one millimetre "blinks", aperture jitter crossing the blink line again and again, each crossing counted. The textbook answer is hysteresis, the thermostat's trick: switch on at one line, off at another, and the gap buys silence. So the first design latched a closed eye closed until the aperture rose ten percent ABOVE the threshold. It passed every test. Then twenty two review agents attacked it and killed it three ways, each with a reproduced input sequence: the latch stretched measured durations, so a valid blink near the half second limit now measured too long and vanished into no bin at all; the latch had no time bound, so a droop after any closure kept the clock running and fired false long closures, the exact disease amendment 5 had just cured; and once chatter latched the eye closed, a real blink arriving mid ride was folded into the ride and swallowed. The mechanism was wrong, not the parameters. A latch on the reopen side changes WHEN A CLOSURE ENDS, and half this project's numbers are defined by when closures end.
The design that shipped puts the gap on the other side of the line, where no duration lives. Closing and reopening are untouched, both at the original threshold, every duration keeps its 4.3 definition, and the owner's pinned 133 and 117 millisecond blinks still measure 133 and 117. What changed is that a closure must now prove its depth: it only arms as a blink candidate once the aperture reaches the threshold minus ten percent. Chatter dips a tenth of a millimetre and never arms, fifty shallow closures count zero. A real blink plunges millimetres past the arm line and counts, even mid ride, because without a latch each shallow dip ends at the next rise and the deep dip stands on its own. The honest cost is narrow and on record: a deliberately shallow closure that bottoms between the arm line and the threshold is indistinguishable from deep chatter and is refused.
Two lessons ride above the mechanism. First, where you put a guard matters more than how wide it is: the same ten percent gap was catastrophic above the line and clean below it, because one side owned the definition of duration and the other owned nothing. Second, passing every test is weak evidence when the tests were written by the design's author in the design's own vocabulary: the three killing sequences all lived outside what I had thought to script, and it took adversaries paid to refute to find them. The long closure detector, which the first design also touched, shipped untouched instead: its chatter risk is real but different, and it is filed where it belongs, in the depth-qualified episode redesign.

## Amendment 6: PERCLOS learns to see, and a tripwire is retired

The concept this fix teaches is the difference between a convention and a measurement, and what it costs to align two instruments.
PERCLOS shipped at 6.1 wearing the literature's P80 convention: closed means below 20 percent of the open baseline. The convention silently assumes an instrument that reads fully shut eyes as nearly zero. Ours does not: the landmark model stops short, reporting shut eyes at about a third of baseline, and so the 20 percent line sat below anything the instrument would ever say. PERCLOS read exactly 0.0 percent through a fully witnessed 12.9 second closure, a measurement that ended the argument. The line is now the same measured 40 percent shut line the long closure detector uses, one constant, aliased, and the owner's blindness experiment is the regression test: six shut seconds in a sixty second window must read exactly ten percent.
The honest bookkeeping: this is no longer literal P80, it is an instrument-adjusted convention, and every document that mentions it now says so. Renaming it would break the connection to forty years of literature; keeping the name while documenting the adjustment keeps both truths.
The subtle cost deserves its own paragraph. Until today, PERCLOS and the long closure detector watched "shut" through different lines, and their DISAGREEMENT was the tripwire that exposed amendment 5's bug: long closures counting seconds while PERCLOS read zero on the same frames was the contradiction that started the investigation. Aligning the lines retires that tripwire on purpose. What replaces it is written down: the regression tests that pin both detectors to the owner's measured scenarios, and the manual items that check them against a live face. Redundancy you understand and retire deliberately is engineering; redundancy you lose without noticing is how the next bug hides. The 6.5 score can now consume PERCLOS without inheriting a permanently zero input, which was the practical point all along.
One more paragraph, because the review of this fix earned it too. The first draft aligned only the FRACTION and left the two detectors on different baselines: the long closure line frozen at the session's first learned baseline, PERCLOS riding the live ratchet. Review reproduced the consequence with the owner's numbers: two seconds of widened eyes ratchets the live baseline past 9.25 mm, and from then on a minute of ordinary reading drives PERCLOS to a saturated false 100 percent while long closures correctly read zero, the old disagreement reborn upside down, under documentation claiming disagreement impossible. The shipped fix freezes ONE baseline and derives both shut lines from it, and aligns the boundary convention at the line (strictly below closes, everywhere). Only then does "cannot drift apart" stop being a wish and start being a property of the wiring.

## 6.4 The record, and the contract that rotted in a drawer

The concept this increment teaches is the schema: the moment measurements stop being lines on a page and become one typed row per second that other code, and later other languages, will trust. Everything the lab computes now lands in a FeatureRecord: sixteen fields, every one nullable where its gate can refuse, because a record that invents numbers is worse than no record. The validator is the border guard: NaN refused everywhere a number lives (NaN is a number to typeof and a lie to arithmetic), infinities refused (JSON cannot carry them), negatives refused where meaningless, missing keys refused, extra keys tolerated deliberately so a future field never makes old records unreadable. When 6.7 serializes these rows and Phase 7's Python loads them, this schema is the treaty both sides signed.
The embarrassing lesson, recorded because it is the valuable one: SPEC.md had declared a FeatureRecord contract since day one, three fields and a plan, and I never read it again after Phase 0. Sixteen increments of fields arrived and the contract document recorded none of them; the adversarial review caught the built type contradicting the founding specification. A contract nobody consults is not a contract, it is a fossil. SPEC.md is now amended to the real shape and to a new duty: it updates when the contract does, or the review will catch it again.
The review also straightened three honesty wrinkles before the pull request: a wrong-count model used to make record seconds vanish entirely while a lost face produced honest null rows, two meanings of untrusted in one pipeline, now unified so every second yields a row; the buffer cap now announces when it starts discarding the oldest hour instead of letting the label claim the full session; and the label says ABOUT one row per second, because the assembly gate re-arms on the firing frame and drifts a minute per hour, which is why durations come from timestamps and never from counting rows.

## 6.5 A number you can argue with

The concept this increment teaches is the difference between a score and an explainable score, and it is all in one identity: the score equals one hundred minus the sum of its named contributions, exactly, always. Most scores are the output of something you must trust. This one is a subtraction you can check by hand, which means a supervisor, a skeptic, or a test can take any score apart into its four parts, eyes closed share, long closures, slow blinks, sluggish lids, and put it back together. The ladder's check is that identity as arithmetic, and the design earns it two ways: the four penalty caps sum to exactly one hundred, so no clamp ever breaks the equation, and every contribution is a whole number of points, so the equation lives in integer arithmetic where floating point cannot smuggle in a hundredth.
The weights are a documented heuristic, chosen and defended, not learned: PERCLOS carries forty points because it is the most validated signal in the drowsiness literature, microsleep-shaped closures carry thirty because each one is an event that matters, and the two blink-shape signals carry fifteen each because they lead the others in time but trail them in specificity. Phase 7 exists to embarrass these weights with data, and the heuristic stays as the baseline any learned model must beat, which is the project's oldest rule wearing its score.
Two honesty rules carried through. No score exists until PERCLOS does, because a score without its heaviest signal would be a guess wearing a number. And an unavailable signal contributes zero points MARKED unavailable, never silently scored as alertness, the difference between "no evidence of drowsiness" and "no evidence at all", which is the difference this whole project keeps insisting on.
The review of this increment taught the sharpest lesson of the three, and it is the same lesson amendments 5 and 6 already taught about thresholds, arriving now dressed as weights. My first draft priced every ramp from the literature's numbers: penalties starting at 60 ms of lid sluggishness and 2 percent PERCLOS. But this project's own manual documents what THIS instrument reads from a rested person: blink A/V from 30 to 150 ms, resting PERCLOS one to three percent. So the ramps began INSIDE the range the same repository calls normal, and an awake person doing nothing wrong could lose fifteen points for blinking naturally. The file even contradicted itself, its comment calling 60 to 150 ms alert while its code charged that range. Every floor now sits above this instrument's documented normal band, and the regression test that guards it is the owner's own resting numbers scoring exactly 100. A score that punishes ordinary life teaches nothing, and the numbers to calibrate against were already written down in our own manual.
Two more catches worth recording. The score was reading a window of sixty ROWS instead of sixty seconds, which quietly bridged a paused tab's ten minute gap and charged a closure from another era; it now selects by timestamp, the rule this project wrote for itself at 6.4 and then broke one increment later. And the score cheerfully scored an empty chair: with nobody there, PERCLOS's ratio climbs on its own as the open samples age out of its window, so the score sank toward maximum drowsiness about furniture. It now refuses when the newest record saw no face, and the underlying PERCLOS behaviour is filed as its own issue rather than papered over here.

## 6.6 Showing the working

The concept this increment teaches is that explainability is not a property of a number, it is a property of what you show beside it. 6.5 built a score that IS an exact sum of named parts. It could still have shipped as a bare 72 out of 100, and a bare 72 explains nothing: the person reading it can only trust or distrust it. The panel spends four lines to change that, and those four lines are the difference between a demo people nod at and a demo people interrogate.
The logic is small on purpose, because it computes nothing: it selects and phrases what the scorer already decided. A driver is a signal that actually cost points, so zero-point and unavailable signals never appear; a signal that drove nothing is not a driver. Ties break by the scorer's own declaration order rather than by name or by chance, which sounds pedantic until you picture the panel re-sorting two equal drivers every second and flickering at a viewer.
The honest limit worth naming: the panel shows the top three of four contributions, so its visible lines deliberately do NOT sum to the score. That is a real tension with the 6.5 identity, resolved by choosing legibility for the panel and keeping the exact identity in the tested core where 6.7's export and Phase 7's analysis will use it. Three lines a person reads beats four lines a person skips, and the fourth is never hidden mischief: it is by construction no larger than the smallest one shown. Review sharpened that sentence from a wrong one. I had written "the smallest", but the cut is not tie-aware, so a hidden driver can EQUAL the last one shown, and a test now pins exactly that case. A documented limit is only worth having if the document states it precisely.
Two sentences carry the project's oldest rule into the panel. "Nothing is costing points." exists so an empty list cannot be mistaken for a broken panel. And "N signals unavailable" exists because absent evidence must be visible: a missing signal is not an alert signal, the same rule the fps gate wrote at 4.6 and every window since has kept. Review caught that sentence misfiring on its own grammar: written as "Top drivers of the score: 2 signals unavailable", the colon promised a list and then delivered a count of the things deliberately NOT in it, so absence read as cost, the 4.6 rule inverted. The colon now always ends the sentence, adjacent to the list it introduces. Copy is part of the contract, and a punctuation mark can undo a design decision.

## 6.7 The border, and why a comma is a security question

The concept this increment teaches is the interchange format: the moment data stops being yours and becomes someone else's input. Everything before this ran inside one program where a number was a number. A CSV file crosses into Excel, into pandas, into a spreadsheet a safety manager opens in three years, and each of those readers will believe whatever the file says. That makes serialisation a contract rather than a convenience.
Most of the work is in the cases a naive join gets wrong, and each one is a small lesson in taking a reader seriously. A null becomes an EMPTY field, never the word "null", because a reader parsing that as a number gets NaN and "nothing was measured" is not a number. A value containing a comma must be quoted or every column after it shifts by one and the row silently means something else. A quote inside a quoted field is escaped by DOUBLING it, per RFC 4180, and getting that wrong corrupts the rest of the line. Line endings are CRLF because the specification says so and because Excel is the most likely first reader. None of this is clever; all of it is the difference between a file and a rumour.
The column list is exported as a constant and tested against the record's own field set, which is the load bearing test of the increment. Without it, a field could join the FeatureRecord and never reach the file, and nobody would notice until Phase 7 went looking for a column that was never written. The type system helps but cannot finish the job: it catches a wrong name and not a missing one, so the test does what the compiler will not.
One honesty rule carried over: an empty session exports null rather than a lonely header, because a file containing only column names claims a recording happened. That is the export's version of a fake zero.
Review found four things worth recording, three of them about a file's obligations to a stranger. The export announced itself as `application/json`, inherited from the fixture recorder it borrowed its download path from, which is wrong precisely at the border where a file's self-description IS the contract. NaN would have serialised as the word "NaN", which pandas reads as a missing value, so a broken computation would have arrived looking exactly like an honest "not measured", inverting the increment's own rule. The filename was built from the frame clock, milliseconds since page load, so a session could not be dated, two sessions could collide by name, and after the one hour cap the name would change on every export because it read the buffer's oldest surviving row rather than the session's start. And the fourth: the column guard had a hole the compiler was supposed to cover. `satisfies` rejects a column name that is not a field, but nothing demanded that every field HAS a column, and an OPTIONAL new field would slip past the runtime test too, because an optional field does not force the test fixtures to change. That is not hypothetical: the very next increment attaches per-session metadata to a per-second record, the natural shape for an optional field. A compile-time exhaustiveness assertion now fails the build if a field arrives without a column, verified by adding one and watching tsc refuse.
And the privacy stance survives its first real test. The file is written by the browser to the user's own disk, through the same local download path the fixture recorder has used since 2.7. Nothing is uploaded, there is no server to upload to, and the export does not change that. The data leaves the browser only when its owner carries it somewhere.

## 6.8 The first label

The concept this increment teaches is the difference between a feature and a label, and why a dataset needs both. Every number until now describes the eyes: how long they closed, where they looked, how the lid fell. Those are features. None of them says whether the person was actually sleepy, and without that, Phase 7 has a pile of measurements and nothing to learn against. The KSS answer is the other half: a person's own report, on a nine step scale used in sleep research since the 1990s, asked once before and once after.
Three decisions carry the increment. The anchors live in code as data, not as prose in the interface, because the anchors ARE the instrument: softening "very sleepy, great effort to keep awake, fighting sleep" into something friendlier would change what people report, and then two sessions would not be measuring the same thing. The scale is ordinal, so only whole steps are accepted, and 4.5 is refused: an average of two answers is not a point on the scale. And a person who declines is recorded as SKIPPED, never rounded to a middle value, because inventing a five would put a fabricated label into a training set, which is the one thing a labelling step must never do.
The shape of the data mattered as much as the values. A KSS answer describes a whole session, not one second, so it must not become a per-second column repeated three thousand times, a lie by repetition that would let a naive model treat one answer as three thousand independent observations. It goes above the header as comment lines, which pandas skips with one argument and a spreadsheet shows as two stray rows a human can read.
The honest limit, stated because Phase 7 will have to live with it: self report is a noisy label. People under-report sleepiness, especially when they are the ones being measured. Two answers per session is a coarse signal, and 7.5's classifier will have to earn its accuracy against exactly this noise. The ladder already plans a second, objective read at 7.x, a reaction time check, and this is the increment that makes the need obvious.

## 6.9 The sentence that closes the phase

The concept this last rung of Phase 6 teaches is that a disclaimer is an engineering artefact, not a legal decoration, and it obeys the same rules as any other shared value.
The words themselves are not new: PROJECT.md has said since day one that this is not a medical device, not a safety product, not for clinical or workplace use. What changed is where they live. They now sit in core as a tested constant with one function returning them, and both the page banner and the README read from that idea rather than keeping their own copy. Three copies of a promise is three promises, and the one that drifts is always the one someone reads. The test states what the notice must contain, so a future reword that quietly drops "not diagnostic" fails the build.
Two placement decisions. The banner is above everything and cannot be dismissed, because a notice that appears only after you start the camera is a notice for people who already decided. And the score line KEEPS its own parenthetical: a number and its caveat should travel together, since the number is what gets screenshotted.
The check the ladder asked for is an end to end assertion, and it is the right one: it loads the real built app, confirms the notice is visible BEFORE any camera permission is granted, clicks it and clicks past it, and demands it survive. That is the difference between a promise and a property.
Phase 6 closes here. The lab now measures a rolling state, scores it, explains the score, records it, labels it, exports it, and says plainly what it is not. Phase 7 is where it finally has to prove any of that is true.

## Fix #122: a number that rose with no evidence

The concept this fix teaches is that a rolling window has two failure modes, and the obvious one is not the dangerous one. Everyone expects a window to be wrong when it holds too little data. The subtler fault is a window that keeps ANSWERING after the data stops arriving, because a ratio over a shrinking denominator is not stable, it drifts.
PERCLOS is the closed share of the last minute. When the face leaves the frame, no new samples are pushed, but the window keeps discarding old ones, so the sample set shrinks from the oldest end. If the last thing observed was a closure, the OPEN samples age out first and the closed share climbs on its own, with no new evidence at all. The owner's own recording caught it exactly: PERCLOS rose from 20.5 to 22.1 percent across eight seconds in which the face was recorded as absent on every row. A number rising while nobody is in the chair.
The fix is a staleness rule, two seconds, generous enough to ride out a blink or a dropped frame and short enough that the drift stays under half a percent before the value is withdrawn. It says the thing this project keeps saying in different words: a measurement that is no longer being made is not a measurement, and refusing beats reporting.
One test in this increment is unusual and deliberate: it PROVES the drift rather than preventing it, asserting that the value two seconds later is strictly greater than the value now, from the same frozen state. That test exists so the bug cannot be quietly forgotten. If someone later removes the staleness rule believing it pointless, the drift test still stands there describing exactly what the rule is for.
Worth noting what did NOT need changing. The 6.5 score already refused to score any window whose newest record had no face, so the headline number was protected before this fix existed. That defence was added because adversarial review reproduced a related scenario in code. This one was caught later, in the wild, by a person exporting a CSV and reading it. Two different nets, and it took both.

## Fix #126: a ceiling for a one way ratchet

The concept this fix teaches is that "never falls" and "may rise without limit" are two rules, not one, and only the first was ever load bearing.
The baseline answers what OPEN means for this person's eyes, and it never falls on purpose: a drooping lid is exactly what later phases want to notice, so it must not be able to quietly lower the bar that would expose it. That much was right. What went unexamined was the other direction. The baseline is a p90, and a p90 is precisely the statistic a brief excursion moves: sixty frames of surprise inside a six hundred frame window lift it a long way, and because the value never falls, the lift lasts the whole session.
Past a certain lift the arithmetic turns pathological. The blink line is half the baseline, and once half the baseline exceeds the resting aperture, the eye reads CLOSED while the person sits there awake. Every closure is then timed from a crossing that happened at rest, so durations inflate, the 400 millisecond shape window fills with resting data and amplitudes flatten toward nothing. The owner's own session did it: a 10.7 millimetre baseline over a 5.25 millimetre resting eye, blink durations reading 216 to 300 against a true 117 to 133, and one logged blink carrying an amplitude of 0.2 millimetres.
The fix is a ceiling built from a statistic with the opposite temperament. The median of the same window barely moves under a brief excursion, so the baseline may not exceed 1.4 times it. The two rules now say something coherent together: the bar may climb when the eye genuinely opens wider, because then the whole window moves and the median moves with it, and may not climb because the eye was surprised for two seconds. The ceiling blocks rises only and never forces a fall, or drowsiness would lower its own bar through the back door.
The lesson worth keeping is about the first attempt, which is recorded in the issue and was thrown away. I first tried to fix the SYMPTOM, moving the blink clock to a deeper line so inflated durations would measure correctly. Adversarial review destroyed it: it fixed only the leading edge, it let phantom blinks slip past the duration filter that had been catching them, and it could count one closure as both a blink and a long closure. A measurement that is being corrupted by its own threshold cannot be repaired downstream of that threshold. Fix the cause.

## 7.1 A second language, and the border between them

The concept this increment teaches is the seam: what happens when one system stops being one system. Everything until now was TypeScript in a browser, and a single toolchain could hold the whole truth. Phase 7 adds Python, because the questions change. The browser asks what the eyes are doing. This asks whether any of it means anything, and that is statistics work with a different ecosystem behind it.
Two decisions define the seam. The languages get separate CI jobs, so they fail independently: a broken plot must never block a fix to the instrument, and the instrument passing must never imply the analysis is sound. And they share exactly one thing, the CSV contract, which is now written in SPEC.md and asserted from the Python side by a test that reads the TypeScript source, extracts the column list, and compares it against what the analysis believes it is reading. A drift between them would otherwise be silent in the worst way: Python would miss a column that was added, or read one that was removed, and the first symptom would be a wrong number in an analysis nobody re-derived by hand. I proved that test by adding a fake column to the TypeScript file and watching it fail, then removing it.
The environment is pinned with uv, which fixes the interpreter version as well as the packages, so a laptop and a CI runner resolve to the same thing from one lockfile. That mattered here: the machine only had macOS system Python 3.9, an end of life runtime that current pandas and numpy no longer support, and building an evaluation track on that would have been a foundation with a crack in it.
The deeper point is about what this phase is FOR. Every number this project displays has been defended by argument so far: a threshold priced against measured ranges, a score whose weights are documented and disputable. None of it has been tested against ground truth, because there was none. Phase 7 exists to make the project falsifiable, and 7.3 is a genuine gate: if no openly licensed dataset with drowsiness labels exists, the plan for 7.4 through 7.7 gets rewritten before a line of it is built. Writing the gate into the ladder before knowing the answer was the honest thing to do, and it is about to be tested.

## 7.2 The loader is where honesty is kept or quietly lost

The concept this increment teaches is that reading data is a place where a project decides what kind of project it is. A loader that half succeeds is worse than one that fails, because the plot still draws and the statistic still prints, and nobody re-derives those by hand. So every malformed shape gets a named refusal: a missing column, an unknown column, columns in the right names but the wrong order, an empty file, a header with no rows, a row with the wrong field count, and timestamps out of order. Each of those would otherwise fail somewhere far away from the cause, or worse, not fail at all.
Two of them deserve their reasoning written down. A header with no rows is refused because it claims a recording that did not happen, which is the same judgement the exporter makes when it writes nothing rather than a lonely header, the rule arriving at the border from both sides. And columns in the wrong order is the nastiest case in the set: every name is present, nothing is missing, and every value lands in the wrong column while the file looks perfectly well formed.
The contract's central rule survived the crossing intact. An empty cell means NOT MEASURED, and pandas spells that NaN, so nothing here turns one into a zero. That is also why the plot shows gaps as gaps: matplotlib breaks the line at NaN, and the picture of a session where the face was lost should have a hole in it.
The first real picture earned its keep immediately. Three panels on one time axis, aperture with both threshold lines drawn, PERCLOS, and blink rate. On the owner's own recording you can watch the baseline ratchet lift the blink line in two visible steps while the shut line stays flat beneath it, which is amendment 5's freeze, drawn rather than argued. And PERCLOS climbing to twenty percent where the eyes were deliberately held closed, then draining. Numbers defended in prose for six phases, finally shown as a shape.
The plot's tests are deliberately smoke tests, and that is a considered choice rather than laziness. Asserting the shape of a picture either pins pixels, which breaks on a font update, or asserts almost nothing. What is worth checking is that a real recording draws without raising, produces a file with content in it, and carries its labels in the title, because a plot without its labels is a pretty shape.

## 7.3 The gate that was allowed to say no

The concept this increment teaches is what a gate is for, and the answer is that a gate you would never let fail is not a gate. This one was written into the ladder three phases before anyone knew the answer, and it failed. No public dataset clears all four requirements at once: face video, a real drowsiness label, per-clip subject identity, and a licence a solo unaffiliated founder can rely on in a public MIT repository.

The finding underneath the finding is an asymmetry that turns out to be structural rather than bad luck. The openly licensed drowsiness datasets have no video: the most permissive licence found anywhere in the search was CC0, on a corpus of EEG, EOG and ECG traces. The cleanest CC BY licences sit on still images labelled for eye state, with subject identity deliberately stripped. Meanwhile every video corpus with a real sleepiness label is behind a signed agreement, an institutional email check, a non-commercial clause, or nothing at all. The reason is not carelessness. Face video is personal data, so the teams that collect it under ethics approval restrict redistribution to keep the promises they made to participants, and the anonymisation that would let them release it freely is exactly what destroys the per-subject identity a leave-one-subject-out split needs. The two goals genuinely conflict, and no amount of searching dissolves that.

Two research habits did all the real work and are worth keeping. The first is that downloadable is not the same as licensed. Several datasets sit on an open link under terms that forbid the use anyway, and one of them, CEW, forbids redistributing even the link. Ease of access says nothing about permission, and treating a working download button as consent is the single easiest way to build something indefensible. The second is to read the licence rather than a summary of it. DROZY is the clearest case: it is widely assumed to be blocked by its no-modification and no-redistribution terms, and neither is true. Computing features leaves the corpus bit-identical, and its citation term expressly contemplates publishing results obtained by using the database. What actually blocks it is the purpose limitation, research and evaluation only, no commercial developments, which sits upstream of both and gates use at all. Getting that right matters, because a project that propagates "DROZY forbids feature extraction" upward has recorded a false reason and will re-derive the wrong conclusion later.

The second pass was adversarial, and it earned its cost twice. NITYMED came back from the first sweep with two contradictory licences, and the tempting reading was that a Kaggle mirror had got it wrong. It had not: the uploader is the rights holder, and the authors' own citation list names that Kaggle release as canonical. Two stable, first-party, contradictory grants, three years old each, with no tie-breaker. But the same pass then showed the conflict barely matters, because NoDerivatives is not NonCommercial and numeric measurements are most plausibly facts rather than adapted material. What actually rules NITYMED out is something nobody had checked: the released directory structure is behaviour, then gender, then resolution, so per-clip driver identity is not recoverable and the leave-one-subject-out split is impossible by construction. The dataset failed on the requirement nobody was arguing about.

The last lesson is about what honesty costs when the answer is inconvenient. UTA-RLDD is the only dataset with the video, the labels and the subject identity this project needs, and the strongest single piece of evidence for using it is that the original authors themselves publish derived numeric features from those exact videos under MIT. That is a real precedent and it makes the path defensible. It does not make it clean, and the difference is not a formality: no licence means no granted permission, the participants' consent terms are published nowhere, and the videos were self-recorded so the copyright chain runs back to sixty individuals whose rights the lab may not fully hold. The recommendation is written down with the counter-case attached, and the decision is left to the person whose repository carries the risk. Writing "defensible, not clean" into the document rather than rounding it up to "fine" is the whole point of the phase.

## 7.0 The clock is the feature, and my first version of it was wrong

The concept this increment teaches is that adding a second source to a pipeline is really adding a second clock, and the clock is where the correctness lives. On the surface this is a small feature: a file input, a video element pointed at a local file instead of a camera, everything else unchanged. Underneath, every rolling measurement this project makes reads one number, the timestamp of the frame being processed, and that number just stopped meaning one thing.

For a live camera the wall clock is right, and it is right for a reason worth stating: the camera and the room share it. A frame that arrives now happened now. A recorded clip shares nothing with the wall. Play it at one times speed and the two agree by coincidence, which is exactly the kind of agreement that hides a bug until the day it stops. The day it stops is increment 7.4, a batch runner, whose whole purpose is processing a ten minute clip in far less than ten minutes. Under a wall clock that clip would report thirty seconds: blink rate twenty times too fast, durations twenty times too short, PERCLOS averaging over a window twenty times too wide. Nothing would crash. Every number would be wrong. So a clip is timed by its own position, and the rule is that the measurement's clock belongs to the thing being measured, never to the machine doing the measuring.

That much I got right. The rest of my first attempt was built on a premise I never checked, and adversarial review took it apart. This is the honest account.

I reasoned that the frame loop runs on requestAnimationFrame at display rate, roughly sixty times a second, so a thirty frame per second clip would offer the same decoded frame to two consecutive ticks, and that reading the clip's own currentTime would make those two ticks carry the same timestamp and become rejectable. Every sentence of that is true except the one that matters. **HTMLMediaElement.currentTime is interpolated from the media clock during playback. It is not quantised to decoded frames.** Review proved it on a real ten frame per second clip: 482 display ticks over two seconds produced 482 distinct timestamps while only 21 frames were actually decoded. My duplicate gate rejected nothing, ever. The instrument would have reported the display's refresh rate as the clip's frame rate, and the frame rate gate that exists to refuse sources too coarse to see a blink would have refused nothing, so a ten frame per second clip would have produced blink durations, PERCLOS and an alertness score as though it had adequate resolution.

The part that should sting is why my test suite was green. I wrote a test that fed the gate the values `[0, 0, 33.3, 33.3, 66.6, 66.6]`, hand-quantised numbers that the real source never emits. I had tested my belief about the world rather than the world. This is the second time in this project: the same note for fix #126 records that my regression test was rigged and review destroyed it. A test whose input you constructed from your own mental model can only ever confirm your mental model.

The real answer is requestVideoFrameCallback, which fires once per decoded frame and hands back that frame's own mediaTime, already frame quantised. So a clip is now driven by its frames rather than by the display, and the display loop returns early in file mode instead of sampling a number that was never trustworthy. Where a browser does not offer that callback the feature refuses to run at all, with a message saying so, because for a measuring instrument refusing is better than reporting the display's refresh rate as a property of someone's recording.

Review found three more things, and each teaches something different.

The clip used to start playing while the model was still downloading, so the opening seconds went by unmeasured. Measured at three and a half seconds, and a short clip could be consumed entirely. For a live camera this is invisible, because the person just keeps sitting there. For a finite recording it deletes the head of the data and nothing in the exported file says why. **A stream forgives latency and a recording does not**, and treating the two as the same source is exactly the class of error this increment existed to avoid.

The export still asked "how sleepy do you feel now?" on a clip session. I had written a careful comment on the file path explaining that asking a viewer about someone else's recording would attach the wrong label to the wrong face, and then left the second half of the same question wired up somewhere else in the file. Writing down the principle is not the same as implementing it, and a comment stating a rule is worth nothing if the code beside it is only half the rule.

The worst one was quiet. resetSession, the block I extracted precisely because I knew shared reset state is dangerous, forgot two rolling buffers. Alone that was harmless. Combined with a clock that now restarts at zero it became data corruption, because the retention filter asked `now - sampleTime <= tenSeconds`, and a subtraction changes sign when the clock jumps backwards. Every stale sample read as negative age and survived forever, so a clip's first blink shape was computed from the previous camera session's aperture trace and exported into the CSV as that clip's. Two individually benign facts, one new, one old, multiplied into a wrong number that nothing on screen would reveal. The fix clears the buffers and makes both filters two sided, because a sample from the future is not a sample, and a guard that only asks "is this too old" is one sign flip away from asking nothing at all.

Finally, the thing I found by accident while fixing the tests, which is now issue #145. A clip played in real time can only be measured as fast as the model runs, and in the test environment the model took 3230 milliseconds per frame against a clip playing at ten frames per second. One frame in nineteen was measured. The downstream behaviour is honest, since the frame rate readout describes frames actually measured and the gate then refuses what is too coarse, but it means the same clip yields different data on different machines. That is the concrete reason 7.4 cannot reuse this path: a batch runner has to step a recording frame by frame and wait for each measurement, so the output depends on the file rather than on the hardware.

The lesson tying all of it together is that this increment looked like plumbing and was actually measurement. Nothing here crashes when it is wrong. Every one of these defects produces a plausible number, and plausible wrong numbers are the only kind this project should genuinely fear.

## 7.4 Making the clip wait for the instrument

The concept this increment teaches is that a measurement which depends on the machine doing the measuring is not a measurement of the thing. Increment 7.0 could read a clip, and it read it while the clip played. That felt natural because it is what a camera does, and it was wrong for the same reason 7.0's clock was wrong: a recording is not a stream, and treating it as one imports a property of the hardware into the data.

The number that made it concrete was wrong the first time I quoted it, and correcting it is part of the lesson. I observed a 1.9 second clip yielding a single measured frame, saw the inference readout showing 3230 milliseconds, and concluded that inference cost three seconds per frame. It does not. That readout is a rolling mean, and with only one or two samples in it, it was reporting the cost of the FIRST inference, which includes the model initialising itself lazily on its first call. I had read a warm-up cost as a steady state cost, from a mean I had watched being computed over almost no data.

Two costs, measured separately rather than conflated. The FIRST inference on a page costs about three seconds, because the model initialises lazily on its first call, and a short clip can be consumed entirely while that happens. Steady state afterwards is about 73 milliseconds per frame on the development laptop, which is above this project's own 30 millisecond budget and caps a watched clip at roughly 13 measured frames per second. So a 30 frames per second recording watched in real time loses more than half of itself, and a 10 frames per second one loses little once warmed up.

The original observation was still real, and the diagnosis was still right for a different reason: that particular clip was 1.9 seconds long and ended entirely inside the first inference. But "one frame in nineteen" is a fact about a short clip meeting a cold model, not a general per-frame cost, and stating it as the latter would have left a wrong number in the project's own documentation about its own performance.

Either way the underlying problem stands. Two people running the identical benchmark on the identical file produce different results, and neither is alerted, because the per-second rows both look perfectly ordinary. That is the failure this project should fear most: not a crash, but a plausible number whose provenance is invisible.

So the direction of the wait is reversed. A stepped run presents one decoded frame, pauses, runs the whole pipeline to completion, and only then allows the next frame. The clip waits for the instrument rather than the instrument sampling whatever the clip happens to be showing. The output becomes a function of the file alone.

One implementation detail is load bearing and easy to get wrong. The pause has to happen INSIDE the frame callback, synchronously, before any await. Pausing after an await hands control back to the browser first, several more frames present in that gap, and the code that looks like careful stepping quietly degrades into the sampling it was written to replace. The fix and the bug differ by where one line sits.

The second half is about what the file says. A CSV from an under-sampled run and a CSV from a complete run are indistinguishable by inspection: both hold honest per-second records, and averaging across them silently mixes two different measurements. So the export now records the mode, the frames actually measured, the clip's length and the resulting rate. The rule this follows is one the project keeps rediscovering: when a number's meaning depends on how it was produced, how it was produced belongs in the file, not in somebody's memory of the afternoon.

Stepping is the default, and the default is an argument about what kind of tool this is. Watching is nicer, and it stays available because filming a jerky one-frame-at-a-time playback would be miserable. But an instrument should be correct unless explicitly told to be pretty, not the other way round.

Worth recording honestly: the test that proves all of this discriminates weakly. Its clip is 10 frames per second, and at 73 milliseconds per frame both watching and stepping measure nearly all of it, so the test passes either way once the model is warm. A test whose power depends on the environment is a weaker thing than one that does not, and naming that here is better than believing the green tick means more than it does. The honest strong test would use a clip fast enough to outrun the model, around 30 frames per second, and assert that watching measures materially fewer frames than stepping. That is left as a known gap rather than claimed.

## 7.4b The stepper did not step, and the owner's own face proved it

The concept this correction teaches is that a test built from your own imagination tests your imagination. This is the third time in two increments, and this time the cost was a false number in a file the owner had already read and believed.

Increment 7.4 promised that a clip would be measured completely, so a benchmark would depend on the file rather than the machine. Its mechanism was to play the clip and pause inside the frame callback, synchronously, before any await. That reasoning was careful and it was wrong, because a playing video advances in real time regardless of what the measuring code does. At sixty frames per second a frame arrives every seventeen milliseconds, and the gap between resuming playback and the pause taking effect is longer than that. Roughly every other frame went past unseen.

The proof arrived as the owner's first real recording: a constant sixty frames per second clip containing 12,626 frames, of which the instrument measured 6,655 and then reported "measured every frame". Fifty-three percent, described as one hundred.

Three failures stack here and each is worth separating.

The mechanism was wrong, which is ordinary. The MESSAGE was wrong in a way that is not ordinary, because it asserted something the instrument cannot know. Software can count the frames it looked at. It cannot count the frames a file contains without decoding the whole file, which is exactly what it is trying to avoid. "Measured every frame: 6655 of them" derived a claim about the file from a fact about itself. The wording now reports the frames measured and the rate they arrived at, and asks the reader to check that rate against a clip they know, because a person who recorded at sixty can tell instantly whether sixty is right.

And the test passed because its clip ran at ten frames per second. At a hundred milliseconds apart, nothing could slip through the gap, so a stepper that lost half of a real recording sailed through. I had chosen a gentle input and then believed the green tick. The replacement pushes frames as fast as the browser will take them and asserts the COUNT, within one, rather than a rate near a number I picked. Verified by deliberately enlarging the seek step and watching it fail at twenty of forty.

The fix is to stop playing the clip at all. Each frame is now sought, and a seek does not care how busy the computer is. Slower per frame, exact regardless.

The part I am least comfortable with is the diagnosis I gave before measuring. Seeing the measured rate wander between eight and forty across the session, I told the owner their camera was variable frame rate and their room was too dark. Both were false. Their recording is rock steady and their room is well lit. The variation was mine, and it tracked how busy their machine was, which they guessed correctly before I did. The lesson is narrow and sharp: when an instrument disagrees with the world, suspect the instrument first. I had a file I could have measured in one command and I offered a theory about their camera instead.

There is also a smaller bug worth recording because it hid in plain sight. The new calibration, which learns a clip's frame interval by seeking forward in small steps, computed each next probe from the media time it landed on. A seek into the middle of frame zero returns media time zero, so the next probe was computed from zero again and the loop asked for the same instant until it gave up. It reported "unknown rate" rather than hanging or lying, which is the right failure, and the fix is to advance from whichever is later, the probe or the frame. A loop whose progress depends on a value that can fail to advance is not a loop.

## 7.4c Safari measured zero frames and called it a measurement

The concept this correction teaches is that "works in my browser" is not a property of software, it is a property of one browser, and a project that tests in one engine has verified one engine.

The seek-based stepper from the previous note was correct, and on Chrome it measured the owner's clip perfectly: 2,402 frames of 2,402, at exactly 60.00 per second. In Safari the same clip on the same machine measured **zero**, in four seconds, and the app printed "Measured 0 frames at unknown rate, in 4 s" as though that were an outcome.

Two distinct faults, and the second is worse than the first.

The mechanical fault: Safari does not fetch a video's data until something asks for it. A stepped run never plays, so nothing ever asked, and every seek sat waiting for bytes that were not coming until the two second timeout fired. Two timeouts, calibration and the first real frame, is exactly the four seconds observed. The fix is to set the element to preload its data and to wait for `canplay` rather than `loadedmetadata`, because metadata gives you dimensions and duration while a stepped run needs actual frames. Separately, browsers disagree about which signal announces a finished seek, so the code now waits for either the frame callback or the `seeked` event and prefers the more precise answer rather than depending on one and hanging when it does not come.

The honesty fault: zero frames is not a measurement, it is a failure, and printing it in the same sentence pattern as a real result made breakage look like data. This is the identical mistake as "measured every frame" two notes ago, in the opposite direction. Both come from software describing its own output without asking whether that output means anything. Zero frames now refuses, with a message saying the file loaded but seeking produced nothing and suggesting what to try.

The process lesson is the one worth keeping. The suite ran in Chromium only, so no amount of green ticks could ever have found this; the owner found it by hand, on the second browser he happened to try. WebKit has now joined the test matrix for the clip tests, and running it immediately reproduced the zero-frame failure against the pre-fix build, which is the confirmation that both the bug and the fix are real. Camera tests stay Chromium-only because WebKit has no fake camera, but clips are exactly where the engines differ, so clips are what runs in both.

One caveat recorded rather than glossed: Playwright's WebKit is not Safari. It is close enough to have reproduced this bug, and it is not close enough to be trusted as proof, which is why a manual Safari pass has been added to the checklist as well.

### Postscript to 7.4c: where the WebKit test ended up

WebKit found the real bug and then cost three more rounds failing for reasons that had nothing to do with the code: no MediaRecorder on a Linux runner at all, and a stepped clip stopping at 27 frames of 60 through fixes to both the calibration and the duration handling. Playwright WebKit on Linux is not Safari on a Mac, and a test that fails for reasons unrelated to the change under review teaches people to ignore red, which is worse than not having the test.

So it runs locally and not in continuous integration. That is a retreat and it is written down as one. The protection now lives in three places of decreasing strength: a local run covers both engines on a Mac, continuous integration covers Chromium, and Safari proper is a manual check, because Playwright WebKit is not Safari either. Naming which of those actually runs on every pull request, and which depends on somebody remembering, is more useful than pretending the coverage is uniform.

## The blink log, and why a second file rather than a wider one

The concept here is that a table's shape encodes a claim about what kind of thing it holds, and choosing the wrong shape loses data silently.

Everything this project exports has been one row per second. That is right for a state: what the eyes were doing during that second is a fair question with one answer. A blink is not a state, it is an EVENT, and events do not fit. At a resting rate of fifteen a minute two blinks land in the same second often enough to matter, and a per-second table keeps one of them. Not with an error, not with a warning: it simply keeps the last one and reads as complete.

So blinks get their own file, one row per blink. The thing that makes it worth building at all is the two frame columns. A human annotator marks blinks by frame number, because that is the only unit a video really has, and a comparison against their work therefore has to happen in frames. Milliseconds look like they would substitute and they do not: our clock and theirs agree only if the frame rate is exactly what both parties assumed, and this project has now been wrong about a clip's frame rate twice in one day.

Two smaller decisions follow the rules the per-second file already set. The frame columns are empty for a live camera, because "frame 900" of a webcam session means nothing to anyone and writing a number there would invite somebody to compare it with something. And a blink whose shape could not be analysed writes empty amplitude, never zero, because zero amplitude is not a missing measurement, it is a claim that the eyelid did not move.

Verified on a real recording rather than asserted: seven blinks across forty seconds, and each frame span agrees with its own duration column. A 133 millisecond blink spans frames 374 to 382, which is eight frames, which is exactly 133 milliseconds at sixty frames per second. That internal consistency is the check that the two numbers came from the same reality.

## The boxed layout, and a bug that six phases of screenshots hid

The concept here is that the arrangement of a page is a claim about what matters, and a page where everything looks equally important claims that nothing does.

Every readout had the same visual weight. The alertness score, which is the entire point of the project, sat in the same size and colour as the frame counter. A stranger watching a demo could not tell in two seconds which number the instrument is actually about, and that is a layout problem rather than a wording one.

The fix is three tiers rather than five equal boxes. The score is the only large text on the page. The measurements sit under it in three boxes of equal weight, Blinks and Eyes and Gaze. The instrument's own reports on itself, frames per second and inference time, go last in smaller grey type, because putting frames per second beside blink rate implies they are the same kind of fact and they are not: one describes the eyes and the other describes the tool looking at them.

Two placements were arguable and both are recorded so they can be argued with. PERCLOS went with Eyes rather than Blinks, because it describes the eyelid's state over time rather than counting events. Head pose and the pose gate went with Gaze rather than with the instrument readouts, because they explain why the gaze lines above them go quiet, and next to frames per second they would explain nothing.

Doing the inventory found two readouts that appeared before a session started, the frame counter and the blink log export. The frame counter is the worse of the two: with no camera running it was measuring the DISPLAY's refresh rate and printing it as the instrument's frame rate. Both were simply missing from a long list of individual hide rules, which is the failure mode of hiding children one at a time. Whole boxes are hidden now, and a container cannot forget a child.

The larger find was accidental and had been there since the first phase. The page set no background colour and no text colour, so the browser painted its own canvas from the viewer's system theme while the text stayed black. On a machine in dark mode the entire page rendered black on black. Six phases of screenshots went past, several of them examined closely by two of us, and neither noticed because it was just legible enough to squint at. The page now sets both explicitly rather than adapting to the theme, because this page's job includes being filmed, and a demo that looks different depending on the viewer's settings is a demo you cannot reason about.

## Fix, the export the privacy rule forgot

The concept here is that a rule written for one thing does not extend itself to the second thing, and the only way to find out is to ask the machine rather than to read the rule.

`.gitignore` refuses `blinklab-session-*.csv`, and the comment above it is good: an exported CSV is measurements of somebody's eyes, this repository is public, and git keeps a file even after a later commit deletes it, so it is refused at the door rather than cleaned up afterwards. That reasoning is exactly right.

Increment 6.7 shipped one export. Then the blink log arrived as a second download, `blinklab-blinks-*.csv`, and nobody added a second pattern. From that day until the August 2026 audit, a user who exported their blink log into the project folder could have committed it. Nobody did. The exposure was real anyway.

What makes this worth a note is how it was found and how badly it was missed. Five auditors read this repository against a privacy constraint. All five checked what leaves the device over the network, because that is the famous version of the question, and the telemetry finding came out of it. None asked what happens to the data that stays. The gap was found by a sixth agent whose only job was to ask what the audit had not looked at, and it took one command: `git check-ignore` on a filename the app actually produces.

So the test does not re-implement git's glob rules. It reads the filenames `main.ts` downloads, hands each one to `git check-ignore`, and asks git, because a re-implementation is one more thing that can be wrong in the same direction as the bug it is checking for. It also carries a guard for itself: a name of the shape a future export would take, deliberately not ignored, must come back trackable. If that ever passes, the rest of the test has stopped meaning anything and is quietly agreeing with everything.

Removing the one-line fix makes two of the eight tests fail, which was checked rather than assumed.

Writing it cost twenty minutes rather than five, for a reason worth recording. The first draft resolved the repository root with `new URL("../../", import.meta.url).pathname`, which percent-encodes. This project lives in a folder called "blinklab build", so that returns "blinklab%20build" and every read fails with ENOENT. `fileURLToPath` is the fix. This is the second time that exact trap has cost this project time; the first was the corpus runner in August. The note is in the guard now, at the line that would otherwise invite it again.

The general lesson is about the shape of the question. "Does data leave?" and "what happens to data that stays?" sound like the same question and are not, and asking only the first one is how a repository ends up with a carefully reasoned privacy rule that covers half of its own exports.

## Fix, saying the true thing instead of the pleasant one

The concept here is that a claim nobody has measured is not a fact, it is a hope with good grammar, and the more central the claim the less likely anyone is to check it.

Six places in this repository said the page sent nothing anywhere. The README twice, the model card twice, the project document, and the notice printed on the page itself. ADR-0002 named the absence of any runtime third-party call as the first good consequence of vendoring the model, and that consequence was the main reason the decision was worth carrying a 3.7 MB binary in git forever.

None of it had been measured. The August 2026 audit measured it: about sixty seconds after the face model is created, the bundled MediaPipe library posts to `odml.pa.googleapis.com` and gets a 200 back. It needs no detections at all, only for the model to exist. The payload is usage statistics, so no video, no image, no landmark and no measurement is in it, and the substance of the privacy stance survives. The sentences did not.

What makes this worth a note is not the defect, which belongs to a dependency and which nobody here wrote. It is that the claim was the single most checkable statement in the project, and the easiest to falsify: open the network tab and wait a minute. Six documents asserted it and no test asserted it. The audit's own plan had a checklist item for runtime network calls, and it found this on the first attempt, which is the argument for having such a checklist at all.

Two decisions inside the fix are worth keeping. The notice now names the reporting rather than denying it, which is a worse sentence to read and the only one that survives a reader checking. And the retired phrases are banned by a test rather than by anyone's memory, because a flat denial is a pleasant thing to write and somebody tidying the README next year would reach for one without knowing it had ever been measured. Writing about the history is still allowed, but the guard cannot tell a confession from a relapse, so the rule is to describe what the page used to deny rather than quote it back.

ADR-0002 was not edited. An architecture decision record is a dated statement of what was decided and what was believed then, and rewriting one to match what was learned later destroys the only thing it is for. It carries a pointer to its successor below a line that says nothing above it changed, and ADR-0004 holds the measurement, the options and the open question of whether the call can be blocked at all.

## Fix, holding the prose to the result file

The concept this fix teaches is that a correction decays and a guard does not, and a project that corrects the same class of sentence twice should stop correcting and start guarding.

The August audit found the numbers right and the sentences around them rotten, five ways at once. STATE.md's own "how the number is produced" command still pointed at the retired dataset folder, so anyone checking the 87.7% headline was handed 82.8% with no explanation. The README paragraph that withdraws the glasses claim printed a stale run's figures while calling them the corrected ones, and drew a conclusion the real numbers point the other way. A section still said the refractory period "is planned and it is not built" twenty-eight lines after three paragraphs describing it built. A citation pointed at a file whose 45 belongs to a different run under a different rule. And three documents carried two different unit test counts, 442 and 461, neither of them the suite's.

Every one of those sentences was true on the day it was written. The run changed underneath them. That is why this fix is mostly not prose: tools/resultGuard.mjs reads docs/eyeblink8-result.txt, the committed result file that was already the single source of truth, and a test fails the build when README, STATE, MODEL_CARD or ARCHITECTURE stops agreeing with it, on the headline, the glasses split, the miss figure, the reproduction directory, and any test count a document dares to state.

The guard proved itself before it was even committed. The documents were updated to say 486 unit tests, which was true at that moment; adding the guard's own nine tests made it 495, and the guard failed the pre-pull-request gates on the author's machine until the documents were bumped. That is the intended shape of things from now on: adding a test while leaving a stale count behind is a red build, not a future audit finding.

One near-miss is worth recording. The first pass at fixing the "restart a run" command pointed it at the CURRENT run's measured folder, which would have been worse than the stale target it replaced: those folders are the evidence behind published numbers, and a restart aimed at one would overwrite it. The command now writes every new run into a new dated folder, and the page says why in one sentence.

## Fix, the ratio measured in the wrong space

The concept this fix teaches is that a proof is only as strong as the place it runs: a test executed where the defect cannot occur does not prove absence, it proves nothing, and it does so while glowing green.

The eye aspect ratio is two lid chords over twice the eye width, and the published definition is pixel geometry. This project computed it directly on normalised landmarks, where x is a fraction of the frame's width and y of its height. On a square frame those are the same unit and nothing goes wrong. On the 16:9 frame every real webcam delivers, they differ by nearly a factor of two, so the displayed ratio read about 1.8 times the standard value, and worse, it changed as the head rolled: measured on the audit's synthetic geometry, 0.593 level, 0.435 at 30 degrees, a 27 percent fall across a range SPEC.md declared invariant by construction. The aperture never had this bug, because aperture.ts converted to pixels first from the day it was written, with a comment warning about exactly this trap. The warning sat one file away from the function that fell into it.

The tilt invariance test had proven the invariance claim at 0, 15 and 30 degrees since Phase 3, and every run was green, because it built its faces on a square 1000 by 1000 frame where the anisotropy cancels algebraically. The audit's verdict was blunt: the test could not fail. It runs at 1280 by 720 now, re-projecting the same synthetic scene the way a widescreen camera would, and reverting the fix makes it fail, which was checked by reverting the fix.

The fix itself is small: eyeAspectRatio takes the frame size and converts each landmark through the same toPixels the aperture uses, moved into geometry.ts so both measurements share one conversion and a third cannot quietly skip it. The on-screen number roughly halves, from about 0.48 to about 0.28, which lands it inside the literature's 0.3 neighbourhood that ear.ts's own comment had promised all along, and inside the manual checklist's 0.25 to 0.45 band, which the old readings violated on 239 of the fixture's 300 frames. Nothing downstream moves: the ratio was display-only, and blink detection has always run on the millimetre aperture.

Two details worth keeping. The old formula is not deleted, it is pinned: the tilt test now carries a second counterfactual, "the bug we did write, and fixed", implementing the normalised-space ratio locally and asserting its 1.78x inflation and 27 percent drift, beside the existing counterfactual for the bug we never wrote. And the new frame-size guard fails closed on NaN, checked by test, because the audit found seven gates in this codebase whose comparisons fail open on NaN, and a gate written after that finding has no excuse for joining them.

## Fix, the stamp that scopes a claim

The concept this fix teaches is that a dated stamp is the cheapest honesty mechanism this project has found: it converts "this document is wrong" into "this document was right on its date", which is a different and much smaller thing.

The proof came from the audit itself. The sleepiness results were published nine hours after MODEL_CARD.md was written, and the card still said unpublished; a skeptic scored that a contradiction until the card's own header, "Written 9 August 2026 against the state of main on that date", refuted the finding: a dated snapshot cannot contradict a file that landed after its date. Meanwhile README.md and STATE.md, with no stamps, collected five genuine defects between them, and STATE.md's "Last commit" line went stale twice more during the remediation itself, once within two merges of being corrected.

So both files carry the stamp now, and the rule is enforced rather than remembered: when a stamped file changes, its stamp must change with it. The guard parses only dates behind the stamp words, so a date in ordinary prose cannot masquerade as a stamp, and it compares against the last commit that actually touched the file, with a day of slack for the timezone gap between a local edit and a squash merge's clock. Continuous integration fetches full history now, because a depth-one checkout reports every file as touched by the tip commit, which would demand a stamp bump on every pull request whether or not the file changed. A guard that lies about WHY it is failing teaches people to ignore it.

The stamp does not keep a document true. Nothing can. It keeps a document honest about WHEN it was true, and it turns the reader's question from "can I trust this file" into "is this date recent enough for my purpose", which is a question a reader can actually answer.

## Fix, the attribution that must travel with the work

The concept this fix teaches is that a licence obligation attaches to the artefact you publish, not to the repository you publish it from, so checking the source tree proves nothing about whether the obligation is met.

This page redistributes Google's work three ways: the MediaPipe library bundled into the page's own JavaScript, the WebAssembly files served beside it, and the face landmarker model committed to the repository and served at its own path. All of it is Apache-2.0, and Apache-2.0's core mechanical demand is that the licence and attribution travel with the redistribution. The audit measured the built output: zero occurrences of the word Copyright in the bundle, no notice file anywhere in dist. The repository's own LICENSE file is MIT and covers only this project's code, so a reader of the published page had no way to learn that most of what their browser just downloaded is Google's, under different terms.

The fix rides the build's own machinery rather than adding any: the notice lives in public/, which vite copies into dist verbatim, so it cannot be forgotten by a build step because it is not a build step. The licence text is the canonical Apache-2.0 copied verbatim from another package's licence file rather than typed from memory, because a hand-typed licence with a small error is a worse artefact than none. And the check runs at both ends: unit tests hold the source file to its claims, including that the paths it attributes actually exist in the repository, and an end to end test fetches the notice from the built, served site, because dist is the only place the obligation is actually discharged.

One near-miss, caught by self-review this time rather than by a skeptic: the first draft of the notice said the MIT licence lives "at /LICENSE", a path the published page does not serve. A false path inside an attribution notice would have been this project's recurring defect in miniature, a claim that reads as checkable and fails the check. The notice now points at the repository instead.

## Fix, the counter that counted intentions

The concept this fix teaches is that a counter's name is a claim, and the claim becomes true at exactly one line in the code: count there, not where counting is convenient. `framesMeasured` was incremented at the top of the frame handler, where every frame passes. But a frame that passes is only a frame that was OFFERED. For seconds after a camera session starts, the face model is still downloading, the handler runs at display rate, and nothing is measured at all. The counter ticked anyway, and the export header wrote the total as `frames_measured`, several thousand phantom frames ahead of the truth on a cold start. The fix moves the increment to the line after the model call returns, because that is the line where "this frame was measured" stops being an intention and becomes a fact.

The deeper lesson came from the review, and it is about refusals. My first version of the repair made the summary of a model-less clip run honest about the count, and the summary machinery then explained the zero with the only story it knew: "stepped at the wrong interval, frames visited twice, the exported file records the measured count and is correct." Every clause false, delivered confidently, beside an export button that sat disabled. I had replaced a lie of success with a lie of diagnosis. Two separate review agents caught it, and the repair is a plain refusal that says what is known, that frames were read and none were measured, and no more than that. A refusal has to be inspected as hard as a result, because a wrong explanation teaches the operator something false with the full authority of an error message.

Two smaller habits are worth keeping. The test probe for the counter starts EMPTY and only a real frame writes "0", because a probe initialised to "0" makes a dead wire indistinguishable from a measured zero, which is this project's recurring defect in one character. And the check was proven able to fail twice, once by hoisting the increment back out of the guard and once by deleting the probe write, because a check that has never been red is a claim, not a check.

## Fix, the failure that had no state

The concept this fix teaches is that reporting a failure is not one job but two: the message that says what happened, and the way back. A failed model download used to be swallowed into the console, so the camera session ran forever looking healthy, every readout saying "measuring..." for a measurement that could never come. The fix is a real state, modelFailed, with a sentence a person can act on and a retry button named inside that sentence. A message without a way back strands the user; a retry without a message asks them to trust a button they cannot explain.

The retry itself taught the second lesson: resume through the front door. My first draft resumed the camera session in place, checking only that a stream was still attached to the video element. Review pointed out that attachment is not liveness: the failure window is exactly when laptops sleep and webcams get unplugged, and a retry would have resumed "running" over a dead stream, frames of a frozen image measured forever, the same disease through a new door. The shipped retry calls beginCamera again, the same path a first click takes, so a healthy camera restarts cleanly and a dead one gets its own honest state from the machinery that already knew how to say it.

Two ripples are worth keeping. First, a fix that adds a terminal state must teach every waiter that the state exists: the corpus batch runner knew success words and one failure state, and B2's new state would have parked it forever, the exact trap its B1 repair had closed, reopened one increment later. Second, the new state changed what an older test could stage: B1's "no model" test aborted the download, but an aborted download is now a failure with its own ending, so the test stalls the download instead, which is the cold start B1 was always about. A behaviour fix in one place is a scenario change in another, and tests encode scenarios.

## Fix, the loop that died in silence

The concept this fix teaches is that a crash handler has exactly two honest designs and one dishonest one. Honest: let the crash kill the loop and say so, or catch it, stop on purpose, and say so. Dishonest: catch it and carry on, because then the same throw repeats sixty times a second behind a healthy-looking page, and this project has already shipped four defects wearing exactly that face. The frame loop now reports a crash once and stops for good. The message carries the error's own words, because an unnamed internal error can never be reported by the person who saw it, and it promises only what is true: anything recorded before the stop is kept for export, and the export buttons were taught to honour that promise after the new test caught them contradicting it.

The review found the deeper lesson in the seams between drivers. The page has three frame drivers, the display loop, the played-clip loop, and the stepped-clip walker, and my first version contained the first two while the third, the default for clips, still funnelled a mid-run crash into "this file is broken", disabling the export of everything already measured. A containment fix is only as complete as its census of the things that need containing. The second seam was time: a crash does not wait for in-flight work, so a camera request or model download resolving after the crash would have written "running" straight over the failure state. The source-run token from B1 already knew how to make stale continuations harmless, and the crash handlers now bump it, which is one line that closes every such race at once.

The storage half is the same idea at smaller scale. localStorage may throw on read in locked-down browsers and on write when full, and those calls sat inside the frame loop, so a storage exception did not lose a profile, it killed the session. Guarded, a failed read reports as nothing stored, which the page already shows honestly as uncalibrated, and a failed write says so on the calibrate button itself, the one surface beside the feature that a frame loop does not rewrite.

## Fix, the window that remembered the wrong blink

The concept this fix teaches is that a window built from "now minus a bit of history" is only as truthful as its boundaries, and the honest boundary is usually an EVENT, not a duration. The blink shape window reached back a fixed 400 milliseconds behind the closure, on the unstated assumption that the history there was quiet. Between two quick blinks it is not: the previous blink's steeper, deeper descent sits inside the window, the shape analysis finds it, and the second blink was published with its predecessor's peak velocity, three times too fast, its amplitude-over-velocity read as 76 milliseconds where the true figure was 231. The audit called it the one genuine arithmetic error in the project, and its band of contamination is exactly the gap ordinary blinking visits. The fix clips the window at the previous blink's end, an event the blink reducer already remembered, so the correction added no new state at all: review pointed out my first version duplicated that memory in a second variable under the same name, and the shipped version reads the reducer's own field before the step advances it.

The test is the audit's own synthetic trace, rebuilt on an exact 33 millisecond grid where every expected number is hand-computable, and it pins both directions: the clipped window gives the second blink its own three columns, and a counterfactual keeps the old contamination alive in the suite, bit for bit, so the mechanism stays understood. One honest limit is recorded in the code: a closure the reducer refused, too long or inside the refractory, leaves no end time behind, so a window opening right after one can still see it. The clip covers every counted blink, which is what the export publishes.

## Fix, the button that came back for nobody

The concept this fix teaches is that two rules writing one property need a meeting point, or the stricter rule quietly wins forever. The heatmap button had a real refresh at startup, reading the stored calibration profile, and a real force-off for every off-duty state. But the force-off ran last on every state change, and the only other refresh sat behind a fresh calibration solve. So for a returning visitor the sequence was: enabled at load, forced off at the first render, and never touched again. The heatmap, and the scanpath replay behind it, were unreachable on every visit after the first, which quietly cancelled two whole increments of the ladder for exactly the visitors who had done everything right. The fix is the meeting point: entering the running state recomputes the button from the same source of truth the force-off overruled.

The test lesson came from review, and it is the sharpest form of the check-that-can-fail rule this project has hit: my negative test asserted the button stays disabled for a never-calibrated visitor, and it was proven green against a button rotted to always-enabled, five runs out of five, because it sampled during the requesting window before the rot could fire. An assertion that something is absent means nothing until the moment the thing WOULD appear has provably arrived. The test now waits for the running state through a button that only enables there, and the same rot turns it red.

## Fix, the constants nothing was holding

The concept this fix teaches is that a test which derives its inputs from the constant it checks is a mirror, not a pin: bend the constant and the test bends with it, green all the way. Every pose gate test computed its angles as the limit plus or minus something, so the audit could open the gate to 89 degrees or slam it to 1 and the suite never noticed, and the 30 second learning window, the time the instrument watches a face before claiming to know its open eyes, could be cut to 1 second the same way. The pins are literals: 20 degrees measures and 21 refuses, learning at 29,900 milliseconds and ready at exactly 30,000. A literal is a small duplication on purpose. It is the test saying these numbers, out loud, so a change has to arrive as a conscious edit in two places rather than a drift in one.

The census came before the tests: bend every candidate in both directions and record what survives, because most of the audit's list turned out to be already pinned and the real holes were three pose axes and one direction of one window. Then the census became a tool, tools/mutationCheck.mjs, which replays all 23 bends and demands a red suite for each. Review promptly demonstrated the tool committing this project's own recurring sin: with the test runner replaced by a nonexistent command it printed all mutations caught, because any nonzero exit read as red. It now proves the unmutated tree green before bending anything, tells a suite that failed apart from a runner that could not run, and refuses loudly in both cases. Even the checker of checks needs its own refusal path, and that is the least surprising sentence this project has ever written.

## Fix, the control that could not testify

The concept this fix teaches is that a negative control needs its own witness, and the witness must hold it from both sides. The shuffled null is the analysis's honesty mechanism: relabel sleepiness a thousand times at random, and if the pipeline still finds the signal, the pipeline is the signal. Nothing tested that mechanism itself. The new test plants a near-perfect relation in synthetic sessions, confirms the signal is really there, and then demands the shuffle destroy it, into a BAND rather than under a ceiling, because the review skeptic built a null stubbed to zero and watched it sail under ceilings alone while claiming chance produces nothing at all. A control that reports too little noise is lying in the same direction as one that misses a signal, and only a floor catches it.

The second half is the starved branch. With fewer than three measured pairs the null answered exactly that stubbed zero, and a zero from the honesty mechanism is the most dangerous number it can emit: it reads as "chance produces nothing", so anything observed clears it. It raises now, naming the feature and the count. One honesty note survived review in the other direction: the published run could never reach that branch, because the main analysis filters starved features before asking for their null, so the raise protects direct and future callers rather than rescuing a published number. The comment says so, because a fix that overstates its own reach is a small version of the disease it treats.

## Fix, the clock the pure functions never checked

The concept this fix teaches is that a guard is only as honest as its statement of scope. The reducers are pure state machines, and pure functions believe whatever clock they are handed: a reopen stamped earlier than the close recorded a blink of minus one hundred milliseconds, found by the 6.2 review, filed as issue #107, and left open for six phases because the real wiring never produces such a clock, the frame door refuses it first. The fix gives each of the five reducers the issue names a one-line contract: a frame stamped earlier than the newest timestamp the state itself carries is ignored, state unchanged, and the ongoing-closure readout answers null rather than a negative, because zero milliseconds and counting would be a wrong number wearing a clamp.

The review's contribution was to measure exactly where that contract ends, and the comments now say so instead of rounding up. An open state carries no timestamp, so a backwards frame arriving while the eye is open is still accepted, and a sufficiently creative sequence can mint an event no one witnessed in that order. Sealing that would mean every state remembering the last clock it saw, a shape change across five modules, bought against a scenario the door already prevents. The guards claim negative durations are dead, the tests prove precisely that claim from both sides of the boundary, and the equal stamp is pinned as processed, matching the exactly-at conventions everywhere else in this codebase. A smaller promise, kept and stated, over a larger one implied.

## Fix, the number that impersonated the camera

The concept this fix teaches is that a readout's name is a claim about provenance, and provenance can differ per mode for one and the same number. "Frames per second" read as the camera's delivery rate. Live, it never was: the handler runs at the display's animation pace, so a 20 frames per second camera showed 70, and the reader concluded the camera cleared the blink gate when nothing had checked it. The relabel to "Processing rate" is stage one of the audit's riskiest item, deliberately the safe half: it buys no new measurement, it stops the existing number from wearing the camera's name. Stage two, wiring a true camera rate into the gate, stays held for a quiet day on real hardware, because a gate that starts telling the truth will start refusing sessions that succeed today, and the size of that refusal must be measured before it ships.

The review's catch was provenance again, one level deeper: my disclaimer said "the instrument's pace, not the camera's" unconditionally, and for clips that is exactly backwards. A clip's frames are timed by the media clock, by deliberate design from the stepping era, so there the number IS the source's own rate, and on a 15 frames per second DROZY recording the page would have disowned the one number it was measuring correctly. The message is mode-aware now, and the lesson generalises: an honesty label written for one data path can be a fresh lie on another, and the modes have to be enumerated before the sentence is written.

## Docs, the number that outlived the code that made it

The concept this increment teaches is that a published measurement carries a hidden dependency on the code that produced it, and a repository that records the plan, the data and the result can still fail to record that link. The DROZY correlations were measured on 9 August. Three days later remediation B4 clipped the blink shape window, which the audit called this project's one genuine arithmetic error. ## Fix, the data the page kept without ever mentioning it

The concept this increment teaches is that storage is a promise made on the visitor's behalf, and a promise nobody is told about cannot be declined. Since increment 5.4a a calibration wrote two keys into the visitor's browser, the solved gaze profile and the measurements behind it. Both were justified, both stayed on the device, and neither was ever named on the page or removable from it. The audit's Stage E3 asked for two things, an enumeration and a control, and the pairing is the point: a delete button with no list leaves you guessing what went, and a list with no button is a confession rather than a feature. The list lives in `core/storedData.ts` as data, so `docs/UI.md` and the interface render the same source and a third key cannot leave either of them quietly describing two.

Two design choices carry the lesson. The first is that the confirmation is measured rather than assumed: the erase removes both keys, then RE-READS the storage and builds its sentence from what is actually left, because `removeItem` returning quietly proves nothing and a delete that silently does nothing is this project's oldest disease. The second is that "I could not look" and "there is nothing here" are different sentences. Safari's lockdown mode makes localStorage throw on read, and the loaders elsewhere in this codebase fold that into "nothing stored" quite correctly, since the page then simply shows as uncalibrated. Folding it the same way here would produce a privacy control announcing a clean device it was never allowed to inspect, which is the one lie this particular feature exists to prevent. My first draft did exactly that in the button label, disabling it as "nothing stored" whenever storage refused to answer, directly contradicting the summary line above it; both disabled states now say what they actually mean.

The end to end test needed the same care as remediation B5's, for the same reason and facing the other way. Erasing must also drop the profile the running session holds in memory, or the heatmap stays reachable from data the visitor just asked the page to forget. Asserting the button is disabled after an erase passes trivially when no session is running, because the off-duty force-off disables it anyway, so the test starts a camera and waits for the button to become enabled before erasing. Deleting the one line that clears the in-memory profile turns it red, which is how I know the assertion is measuring the fix rather than the layout.

## Fix, the document that could not be wrong

The concept this increment teaches is that a compensating control needs a way to fail, or it is only a promise. `SPEC.md` argues that this project needs no `src/ui` folder because `docs/UI.md` describes the interface instead, and that argument holds exactly as long as the description is true. The file had one commit and fifteen `main.ts` commits behind it, and nothing in the suite could go red when they disagreed. So they disagreed: five boxes described where eight exist, Session placed in a tier of its own when it sits under Alertness, and a whole section for an "Instrument" box that had quietly become the footer of Live signals. Each sentence was written correctly and the page moved underneath it, which is the same disease the result guard was built for, in a different organ.

The check reads the `box("...")` headings out of `main.ts` and holds the document to them in BOTH directions, and the second direction is the one worth arguing for. A missing section is an obvious hole. A section describing something that no longer exists is worse, because it reads as current: a designer planning against "Box: Instrument" would be designing for a box the page stopped building, and nothing about the prose would warn them. Fossils and gaps are both drift, and only checking for gaps would have left the actual defect standing.

One detail decided whether the guard worked at all. `box()` is called two ways in this codebase, on one line for the short boxes and across several for the long ones, and a pattern written for the single-line form finds five of the eight and reports success. That is the same failure this repository keeps meeting from a new angle, so the pattern allows the newline and a test pins both call shapes explicitly rather than trusting the total. A guard whose reader silently matches a subset is not a weaker guard, it is a guard that certifies whatever it happened to look at.

## Fix, the convention that lapsed because it was only a convention

The concept this increment teaches is the one this repository already wrote an essay about and then failed to apply to itself. Entry 0.6 is called "conventions become mechanisms", and its argument is that a rule enforced by intention holds exactly until the day somebody is busy. The Definition of Done said every increment teaches one concept into `LEARNING.md`. It held for about a hundred and thirty pull requests, lapsed at #134, and nobody noticed for weeks. `docs/log.md` lapsed the same way twice: increments 5.6 through 6.1 on 4 August, and then the whole of 9 August, a day that merged twenty pull requests and produced not one line, including the export defect that had been publishing a wrong recall figure and the clock fix that first made the number repeat.

The backfill taught something the ladder itself had wrong. `REMEDIATION.md` recorded the gap as "8 to 10 August". Both of those days are fully logged; the holes were 4 and 9 August. The item had been written from memory of roughly when things went quiet rather than from the file, which is the identical failure to the one the entries were being written about, one level up. Every backfilled line carries the date it was actually written, because a log line that silently claims to be contemporaneous is a small forgery, and this project's whole argument is that the record is worth more than the appearance of one.

The mechanism has an escape hatch on purpose, and the escape hatch is the interesting design decision. A rule with no way out does not produce more learning entries, it produces filler: a paragraph written to satisfy a check, in the one file a reader is supposed to be able to trust. So a pull request that changes `src/` may instead write "No LEARNING entry:" followed by a reason, in a commit message rather than a pull request body, so the justification lives in the repository and `git log` still explains the gap years later. The marker alone is refused, with a test pinning that, because the shape of a reason is not a reason. And the guard was checked against real history rather than invented cases: it passes the increment that shipped an hour earlier and it catches #233, which changed two source files and taught nothing on the record.

## 8.6 and 8.7 Two numbers that can only move one way

The concept these two increments share is the ratchet: a measurement that is already good, written down as a floor or a ceiling so it cannot quietly get worse. Neither is work in the usual sense. `src/core` was already at 98.61 percent of statements and the bundle was already 217 kB. What did not exist was anything that would notice the day either changed, and a number nobody is holding is a number that drifts.

The interesting decisions were about scope and slack, and they pull in opposite directions. Coverage is measured on `src/core` alone, the pure layer, because the alternative is including `main.ts` and then choosing between a floor low enough to permit anything and a sudden demand to unit test 2,900 lines of DOM wiring the end to end suite already drives. The functions threshold sits at exactly 100, where it already was, because a pure function no test calls is a function nobody has checked and letting that slide is precisely how core stops being the layer you can trust. The bundle ceiling goes the other way and is deliberately loose, 240 kB against 217 kB. It is not written against slow creep. It is written against the single commit that imports the 3.7 MB face model or the 33 MB WASM folder, both of which are served from `public/` on purpose: every test would still pass and the download would be twenty times bigger. A budget tight enough to fail on ordinary work gets raised without being read, and then it is decoration.

Two details keep the budget honest. Chunks are summed rather than judged one at a time, because a check on the largest file alone is satisfied by splitting one oversized bundle in two, which changes what the browser downloads not at all. And an empty `dist` fails rather than passing: zero bytes is trivially under any ceiling, so a missing build would otherwise report as a green check, this project's recurring defect in its purest form. Both guards were proven able to fail before being trusted, the floor by raising it to 99.9 percent and the ceiling by lowering it to 100 kB.

## Fix, a measurement without its conditions is not a measurement

The concept this increment teaches is that a number and the circumstances that produced it are one fact, not two, and separating them destroys the number. A camera session's export used to say `source: camera` and then almost nothing: `duration_seconds` and `measured_fps` were filled in only for clips, because they were computed from a loaded clip's duration, so a live session carried no rate at all and no word about the camera. Six exports from six people would have arrived as six anonymous columns of millimetres with no way to tell a full-frame mirrorless at 60 frames per second from a 480p laptop camera in a dim kitchen. Every one of those numbers would have looked comparable and none of them would have been.

The field worth naming is the median iris width in pixels. The iris is the ruler this whole instrument divides by, so how many pixels it spans across a session IS the resolution of every millimetre it reports. Two devices are only comparable once that is written down. Two others earn their place for narrower reasons: the camera's own declared frame rate, which is a completely different number from the animation rate the page has always shown and which turns remediation D1's held blast-radius question into something measurable on other people's hardware; and `deviceId`, which is deliberately absent, because a stable per-origin identifier for one camera is a fingerprint rather than a measurement and nothing in the analysis needs it.

The marker is the part I would have missed. A validation protocol asks someone to blink deliberately ten times so that ten is known ground truth, and I had planned to find those ten in the export by looking for a burst of ten detections. That is circular: it uses the instrument's own output to locate the event that tests the instrument, and it fails precisely when the instrument missed them, which is the only interesting case. A marker breaks the circle, and the truth becomes "ten blinks between marker 1 and marker 2" whatever the detector thought. The end to end test then caught the implementation being wrong in a way no unit test could: the device block was read before `resetSession()` ran, so the reset silently wiped it, and every field a camera session was supposed to record came out missing while the rest of the file looked perfectly healthy.
