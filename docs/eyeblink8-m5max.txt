EYEBLINK8 ON THE M5 MAX: THE PREDICTION, COMMITTED BEFORE THE RUN

Written 24 August 2026, before the corpus has been measured on the
new machine. The dataset was re-downloaded from its public source
(the previous copy is on a machine that is not physically
accessible); the measured outputs are generated fresh, as they
always are. The run this predicts:

    npm run build
    npm run preview -- --strictPort        (in its own terminal)
    node tools/measure_corpus.mjs \
        "$DATASETS/eyeblink8/eyeblink8" \
        "$DATASETS/eyeblink8-measured-m5max"

    cd analysis
    PYTHONPATH="$PWD" .venv/bin/python tools/evaluate_eyeblink8.py \
        "$DATASETS/eyeblink8/eyeblink8" \
        "$DATASETS/eyeblink8-measured-m5max"

THE PREDICTION. The published table reproduces: recall 83.6% (341 of
408), precision 84.0% (65 invented), F1 83.8%, and the per-clip
found/miss/false counts in docs/eyeblink8-result.txt, identically.
The design says machine speed cannot matter: every frame is SOUGHT
on the clip's own clock, the model clock is offset-stable, and the
whole delivered-rate question does not exist for a stepped clip.

THE STATED THREAT TO EXACTNESS, named before the numbers exist so a
deviation cannot be explained after the fact: the face model's
arithmetic may differ across CPU generations and browser builds in
low-order bits, which moves apertures by micrometres, which can flip
a detection that sits exactly on a threshold. So:

  - identical counts CONFIRM the design claim outright;
  - a difference of a FEW blinks on threshold-hugging clips, with
    coverage counts identical, indicates landmark-level numeric
    drift between machines, NOT an instrument change — it would be
    recorded as a bound on cross-machine reproducibility, a number
    this project has never had;
  - coverage counts differing AT ALL (the measured-frames column),
    or counts moving by tens, is a real defect and stops the line.

Whatever happens is appended below this line as a dated RESULT
section, and this prediction is not edited.

ADDENDUM, 24 August 2026, still before the measurement. The first
attempt printed "0 clips to measure": the runner wants flat .mp4
files and the public dataset ships nested .avi files, so the
published reproduce command depended on an undocumented conversion
whose settings are lost with the inaccessible machine (issue #309).
This run therefore RE-CONVERTS, with the settings recorded here:

    ffmpeg -i <clip>.avi -an -c:v libx264 -crf 10 -preset slow <clip>.mp4

one flat .mp4 per .avi, basenames preserved, audio stripped, frame
timing untouched. This adds a SECOND stated threat to exactness,
named before the numbers exist: the original run also measured
converted files, and two transcodes of the same source need not
produce identical pixels, so the "a few blinks on threshold-hugging
clips" outcome now covers transcode variance as well as CPU-level
numeric drift, and the two cannot be separated by this run. What
transcoding CANNOT change: the frame count the stepper visits, so
the coverage columns must still match the annotations exactly, and
a coverage mismatch still stops the line.
