EYEBLINK8 ON THE M5 MAX: THE PREDICTION, COMMITTED BEFORE THE RUN

Written 24 August 2026, before the corpus has been measured on the
new machine. The dataset was re-downloaded from its public source
(the previous copy is on a machine that is not physically
accessible); the measured outputs are generated fresh, as they
always are. The run this predicts:

    npm run build
    npm run preview -- --strictPort        (in its own terminal)
    node tools/measure_corpus.mjs \
        "$DATASETS/eyeblink8/eyeblink8" \
        "$DATASETS/eyeblink8-measured-m5max"

    cd analysis
    PYTHONPATH="$PWD" .venv/bin/python tools/evaluate_eyeblink8.py \
        "$DATASETS/eyeblink8/eyeblink8" \
        "$DATASETS/eyeblink8-measured-m5max"

THE PREDICTION. The published table reproduces: recall 83.6% (341 of
408), precision 84.0% (65 invented), F1 83.8%, and the per-clip
found/miss/false counts in docs/eyeblink8-result.txt, identically.
The design says machine speed cannot matter: every frame is SOUGHT
on the clip's own clock, the model clock is offset-stable, and the
whole delivered-rate question does not exist for a stepped clip.

THE STATED THREAT TO EXACTNESS, named before the numbers exist so a
deviation cannot be explained after the fact: the face model's
arithmetic may differ across CPU generations and browser builds in
low-order bits, which moves apertures by micrometres, which can flip
a detection that sits exactly on a threshold. So:

  - identical counts CONFIRM the design claim outright;
  - a difference of a FEW blinks on threshold-hugging clips, with
    coverage counts identical, indicates landmark-level numeric
    drift between machines, NOT an instrument change — it would be
    recorded as a bound on cross-machine reproducibility, a number
    this project has never had;
  - coverage counts differing AT ALL (the measured-frames column),
    or counts moving by tens, is a real defect and stops the line.

Whatever happens is appended below this line as a dated RESULT
section, and this prediction is not edited.

ADDENDUM, 24 August 2026, still before the measurement. The first
attempt printed "0 clips to measure": the runner wants flat .mp4
files and the public dataset ships nested .avi files, so the
published reproduce command depended on an undocumented conversion
whose settings are lost with the inaccessible machine (issue #309).
This run therefore RE-CONVERTS, with the settings recorded here:

    ffmpeg -i <clip>.avi -an -c:v libx264 -crf 10 -preset slow <clip>.mp4

one flat .mp4 per .avi, basenames preserved, audio stripped, frame
timing untouched. This adds a SECOND stated threat to exactness,
named before the numbers exist: the original run also measured
converted files, and two transcodes of the same source need not
produce identical pixels, so the "a few blinks on threshold-hugging
clips" outcome now covers transcode variance as well as CPU-level
numeric drift, and the two cannot be separated by this run. What
transcoding CANNOT change: the frame count the stepper visits, so
the coverage columns must still match the annotations exactly, and
a coverage mismatch still stops the line.

RESULT, 25 August 2026. The run happened. The prediction is WRONG,
and wrong in the direction that is hardest to be honest about: the
instrument scored BETTER than the table it was predicting.

  measured on the M5 Max          predicted (the published table)
  Recall     85.0% (347 of 408)   83.6% (341 of 408)
  Precision  96.4% (13 invented)  84.0% (65 invented)
  F1         90.4%                83.8%

Per clip, found and false, published then measured:

COVERAGE IS IDENTICAL. Every clip's measured-frames count matches
the published run exactly — 15784, 11182, 9216, 5405, 10663, 5134,
9077, 4895 — against the same annotated counts. The stepper visited
the same frames, so nothing here is about which frames were seen.
That clause of the pre-decision did not fire.

THE OTHER CLAUSE DID. "Counts moving by tens is a real defect and
stops the line." Fifty-two false alarms disappeared. That is not the
"few blinks on threshold-hugging clips" that landmark-level numeric
drift or transcode variance was allowed to explain, and the shape is
not noise either: the losses concentrate exactly on the clips that
had the most false alarms (19 -> 3, 14 -> 1, 11 -> 0), which is what
a MECHANISM change looks like, not a jitter.

So the pre-registered verdict is applied as written: THIS STOPS THE
LINE. The published table is not reproduced. The new numbers are NOT
published as a replacement, do not enter README, STATE or the model
card, and 83.6 / 84.0 / 83.8 remains the project's standing result
until this is explained. A better number arriving unexplained is
still an unexplained number, and this is precisely the moment a
project stops asking questions because it likes the answer.

WHAT IS ACTUALLY IN QUESTION. Two things changed between the
published run and this one, and only one of them can be the cause:

  1. THE CODE. Thirteen commits touched src/ after the published run
     (003184a, the re-arm gate). Among them, one rewrote every
     timestamp the face model receives (1761e33, the model-clock
     ratchet) and one moved the baseline birth arithmetic into its
     own module (89658cb). Both are supposed to be behaviour
     preserving on a stepped clip. Supposed to is not measured.

  2. THE FILES. These clips were re-converted, because the original
     conversion's settings are lost with the inaccessible machine,
     and the addendum above named transcode variance as a threat.

They are separable, and cheaply, by ONE experiment: check out
003184a, build it, and measure THESE files with THAT code.

  - old code, new files, gives ~65 false alarms -> the files are
    innocent and an increment changed the instrument's behaviour
    without anybody noticing. Whichever commit it is owes a test.
  - old code, new files, gives ~13 -> the code is innocent and two
    transcodes of one recording differ by fifty-two false alarms,
    which is a far larger transcode sensitivity than this project
    has ever assumed, and a finding in its own right.

Filed as an issue. Until it is answered, this document is the
record: a prediction committed before the run, and a measurement
that broke it.
