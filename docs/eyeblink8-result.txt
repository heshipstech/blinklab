BLINK DETECTION vs Eyeblink8 ground truth

Measured 9 August 2026 on a verified build. This REPLACES an earlier
result of recall 69.6%, precision 86.3%, F1 77.1%. That earlier result
was produced before pull request #172 fixed the blink log defect. The
defect deleted the earliest rows from any clip where the app made more
than 50 detections, before the file was written. That hit three clips.
In two of them the deleted rows were real blinks, so those two were
scored against a record that was missing its start. See the README for
the plain English account.

THE LAST DIGIT DOES NOT REPEAT. This is one run, not a fixed value. The
same clip re-measured on the same computer and the same build gives a
different answer. One of the eight clips went from 7 false alarms to 9.
Carried into the totals below that reads 86.0% precision and 84.4% F1
instead of 86.4% and 84.6%. Recall stayed 82.8% in every re-run. Read
the last digit of precision and F1 as approximate.

Totals: 71,356 frames measured against 71,354 annotated. Two clips gave
one frame more than their annotation file lists. Every other clip is
exact.

The two clips the defect cut short are 26122013_224532_cam, which moved
from 55.7% recall to 89.8%, and 27122013_153916_cam, which moved from
58.3% to 91.7%. That is 30 and 24 blinks recovered, 54 in total, which
is the entire move from 284 found to 338. Every other clip found
exactly the same number of blinks in both runs.

CAVEAT. The two runs were built from different commits, so they are not
one measurement with a single line changed. Four of the six shorter
clips shifted a blink edge by a frame or two, or split one detection
into two. Two report exactly the same blink timings. The blink log cap
counted detections, not annotated blinks, so it also bit
27122013_152435_cam, which made exactly 50 detections and lost the
opening rows of its log. How many is not recoverable, because the
capped export is the only surviving record of that run. What is certain
is that the rows it lost were false positives, so no recall figure
changes. The frame rate is not the cause either:
measured_fps is 30.00 in both runs for all eight clips. The recall
attribution above is nevertheless exact.

Two further figures computed from these files:
  55 of the 70 misses, 78.6%, contain at least one frame the human
    marked fully closed.
  38 of the 53 invented blinks sit on top of a real blink, counted the
    strict way: take the detection exactly as reported, widen nothing,
    and ask whether it shares at least one frame with a blink the human
    marked. Allowing this project's own four frame tolerance raises it
    to 45. The stricter number is printed first because that tolerance
    exists to stop a correct detection being punished over an edge, and
    reusing it to decide what a WRONG detection sat on is a different
    act. Either way it is double counting, not invention from nothing.
    Not yet fixed. See issue #176.
