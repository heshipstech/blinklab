THE CAUSE IS THE MACHINE, established by measurement rather than by
assumption. The code was cleared by running the published run's own
code on these files: it produced the M5 Max numbers, not these ones.
The files were cleared by a four-point transcode sweep from lossless
to visibly lossy, where the worst disagreement is ONE false alarm
against a gap of fifty-two. The face model is a committed file and
package-lock.json has not moved since the published run's commit, so
the model, its runtime and the browser build are pinned identical.
What is left is the processor, the operating system, and the browser
binary built for them.

THE REPRODUCIBILITY BOUND, which is the number this pair actually
buys. Across two machines, one corpus, identical frames:

  found blinks       341 vs 347, a spread of 6 in 408   (1.5%)
  false alarms        65 vs 13,  a spread of 52         (400%)
  recall             83.6% vs 85.0%,  1.4 points apart
  precision          84.0% vs 96.4%, 12.4 points apart

Recall travels. Precision does not. Stepping every frame removed the
hardware dependence it was designed to remove — which frames are
read — and did not touch the one that decides precision: a false
alarm is near-line flutter, and whether flutter crosses the line is
settled by micrometres of aperture that differ between machines.
Frame determinism was achieved and read as measurement determinism.

WHICH NUMBER THIS PROJECT PUBLISHES. Both, each named with its
machine, because neither is "the instrument's number" and printing
one alone would repeat the mistake this pair exposed. The headline
stays on the old machine's table for one narrow reason, stated
rather than dressed up: the analysis behind this file's miss
breakdown was run on that measurement and not on the new one.
Promoting the M5 Max table means re-running that analysis first,
not preferring the better-looking column. The better-looking column
is exactly the one to distrust.

A CORRECTION TO BOTH CORRECTIONS ABOVE, 26 August 2026. The 24
August note says the conversion between the public download and this
runner "was committed nowhere" and that its settings "are lost". Both
statements are false. analysis/tools/prepare_eyeblink8.py has carried
that step since #158, with its own dependency group in
analysis/pyproject.toml, and it REMUXES rather than re-encodes: the
H.264 bitstream copied byte for byte, the timeline normalised to
zero, the decoded frame count verified on both sides. Nobody looked
in analysis/tools. Issue #309 was filed on the false premise and
docs/eyeblink8-preparation.txt was written to it.

The consequence for the section above is specific and it is not
cosmetic. The second machine measured RE-ENCODED files; the published
run measured REMUXED ones. The transcode sweep offered as clearing
the files swept four re-encodes and never the remux, so "the cause is
the machine" rests on an incomplete elimination and is SUSPENDED
until the committed tool's own output is measured on the second
machine. The pair of tables above is unaffected — both were measured,
both are real — but the CAUSE printed between them is not yet
established. See docs/eyeblink8-m5max.txt for the command that
settles it.

THE SUSPENSION IS RESOLVED, 26 August 2026: THE CAUSE WAS THE
FILES, AND "THE MACHINE" IS REFUTED. The committed preparation tool
rebuilt the corpus by remux on the second machine, and one clip
answered the question by the rule stated before the number existed:
27122013_152435_cam measured found 36, miss 5, false 19 — the row in
the table at the top of this file, DIGIT FOR DIGIT, on different
hardware. The 12.4-point precision gap between the two tables above
was never machines. It was preparations: the second machine's table
was measured from RE-ENCODED derivatives, while this file's table
was measured from the committed remux, and re-encoding collapses
this clip's false alarms from 19 to 3 at every quality from lossless
to visibly lossy. The second table stays published as what it is — a
real measurement of the wrong files, and the discovery of a
preparation sensitivity nobody suspected — but it is NOT an
Eyeblink8 result and the machine-conditionality read of the pair is
withdrawn. The full-corpus remux run on the second machine, scoring
the prediction docs/eyeblink8-m5max.txt committed on 24 August, is
in progress as this is written; its result will be recorded here.

TWO INSTRUMENT CHANGES IN ONE DAY, EACH MEASURED SEPARATELY

On 20 August 2026 the six-person validation round reported
(docs/validation-round.txt), and two of its findings became code the
same day, each with predictions committed before its own corpus run:

1. THE RULER FROZE (docs/baseline-freeze.txt). The baseline the blink
   line is half of used to rise during a session, and had risen on
   every one of the eight clips, so part of the previous 87.7% recall
   was earned by a line that grew more permissive as each clip went
   on. Frozen at its thirty-second calibration, recall fell to 83.6%,
   inside the predicted band. One prediction was wrong: precision
   FELL, because the frozen lower line exposed near-line flutter
   fragmenting into re-crossings, the very signature the round's P1
   produced live.

2. THE RE-ARM GATE (docs/blink-rearm.txt). After a counted blink, no
   new closure may arm until the aperture rises 10 percent above the
   line, symmetric to the arm line below it. The eyelid must actually
   reopen before it can blink again. Removed 13 false alarms at ZERO
   recall cost, eleven of them fragments sitting on real blinks. The
   refractory period stays at 150 ms: the re-crossings are removed by
   mechanism, not by timer.

This run repeats: measuring one clip three times produces identical
files, byte for byte, a property held since pull request #189.
