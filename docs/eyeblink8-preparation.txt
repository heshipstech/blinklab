EYEBLINK8: FROM THE PUBLIC DOWNLOAD TO A MEASURABLE FOLDER

Written 24 August 2026, the day issue #309 was found: the published
"HOW TO REPRODUCE THIS EXACTLY" depended on a conversion step that
appeared nowhere in this repository, so it reproduced only on the
one machine that already held the prepared folder. This file is that
step, committed.

WHERE THE DATASET COMES FROM. Eyeblink8 is a public research
dataset: eight webcam recordings, 408 human-annotated blinks,
downloadable from the blinkingmatters.com research page. Download
the dataset archive and nothing else: the same site distributes a
commercial blink application, and its installer is not the dataset.
The dataset is a zip of folders; nothing about it installs.

WHAT THE DOWNLOAD LOOKS LIKE. Extracted to $DATASETS, it is one
folder per subject, each holding a recording as .avi beside its
annotations:

    $DATASETS/eyeblink8/eyeblink8/
        <subject>/
            <clip>.avi  <clip>.tag  <clip>.txt

Eight clips across the subject folders.

WHAT THE INSTRUMENT NEEDS INSTEAD. Two tools read this corpus and
they want different halves. The measurement runner
(tools/measure_corpus.mjs) reads FLAT .mp4 files at the top of the
folder it is given: .mp4 because the measuring browser does not
play these .avi files, flat because the runner deliberately reads
one directory level and no more. The evaluator
(analysis/tools/evaluate_eyeblink8.py) reads the .tag annotations
wherever they sit below that same folder. So one folder serves
both: the subject folders keep the annotations, and a converted
flat copy of each clip sits beside them.

THE PREPARATION, EXACTLY. With the download extracted as above and
ffmpeg installed:

    cd "$DATASETS/eyeblink8/eyeblink8"
    for f in */*.avi; do ffmpeg -y -i "$f" -an -c:v libx264 -crf 10 -preset slow "$(basename "$f" .avi).mp4"; done

One flat .mp4 per clip, basenames preserved, audio stripped
(nothing here reads audio), H.264 because every browser this
project measures in decodes it, CRF 10 because it sits near the
lossless end of the scale: the conversion exists to change the
container, not the pictures. Check it worked; expect eight names:

    ls "$DATASETS/eyeblink8/eyeblink8"/*.mp4

WHAT THIS DOES AND DOES NOT PROMISE. These are the settings of the
24 August 2026 re-conversion and the committed standard from that
day on. They are NOT provably the settings behind the published
numbers: those conversions were never committed and their settings
are lost with the machine that ran them (issue #309) — the same
loss covers the `eyeblink8-mp4` folder that older operational notes
name. Two consequences, both stated in docs/eyeblink8-m5max.txt
before any new number existed: re-encoded pixels need not match the
original run's re-encoded pixels, so a small count drift on
threshold-hugging clips cannot be separated into transcode variance
and CPU-level numeric drift; and what a transcode CANNOT change is
the frame count the stepper visits, so the evaluator's coverage
columns must still match the annotations exactly, and a coverage
mismatch stops the line.

A CORRECTION, 26 August 2026: THIS DOCUMENT PRESCRIBED THE WRONG
CONVERSION, AND ITS PREMISE WAS FALSE.

Everything above was written on the belief that the corpus
preparation had never been committed and that its settings were lost
with an inaccessible machine. That belief was wrong. The step was in
this repository the whole time:

    analysis/tools/prepare_eyeblink8.py

committed with the corpus runner itself (#158), with its own
dependency group in analysis/pyproject.toml ("uv sync --group
corpus"). Nobody looked in analysis/tools. Issue #309 was filed on
the false premise, and this file, the correction it added to
docs/eyeblink8-result.txt, and the addendum in
docs/eyeblink8-m5max.txt all inherit it.

WHAT THE COMMITTED TOOL ACTUALLY DOES, and it is not what is
prescribed above. It REMUXES: the H.264 bitstream is copied byte for
byte into an MP4 container, "-c:v copy", never re-encoded. Its own
docstring says why, and the reason is the strongest one in this
project: the ground truth is indexed BY FRAME NUMBER, so a conversion
that dropped, duplicated or resampled a single frame would silently
shift every annotation against the video and produce a confident,
wrong accuracy figure. A remux cannot do that, and the tool verifies
the decoded frame count on both sides rather than trusting the claim.

The re-encode prescribed above is exactly the class of conversion the
tool exists to avoid.

AND IT NORMALISES THE ORIGIN. The committed remux passes
"-avoid_negative_ts make_zero -muxpreload 0 -muxdelay 0", and its
comment explains: remuxing from AVI can leave a start offset, one
clip here began at 1.633 s, "Chrome silently clamps every earlier
seek to the first frame, while Safari never answers them at all. Both
report `seekable` as starting at zero regardless, so the code cannot
even detect the situation."

That is a word-for-word description of the failure that consumed 25
August: eight clips refusing, every seek finishing, no frame ever
arriving, `seekable` reporting 0.00 for a file whose first frame sits
at 1.700. The re-encode above reintroduced the exact hazard the
committed tool was written to remove, and then the instrument was
changed to survive it.

WHAT STANDS AND WHAT DOES NOT. src/core/frameSearch.ts stands on its
own merits: a clip with a real start offset should be measurable
rather than refused, and the August audit had already flagged the
matching inconsistency in the stepper's inexact-landing fallback.
But it was NOT needed to measure this corpus, and the story told in
its commit message — that the corpus clips legitimately begin 1.7
seconds in — describes files this project should never have made.

THE CORRECT PREPARATION, superseding everything above:

    cd analysis
    uv sync --group corpus
    uv run python tools/prepare_eyeblink8.py \
        "$DATASETS/eyeblink8/eyeblink8" \
        "$DATASETS/eyeblink8-mp4"

It prints "N frames in, N out, OK" per clip and refuses to bless a
file whose count changed. The measured folder that produced the
published table came from THAT, which is also why the old operational
note named a folder called eyeblink8-mp4.
