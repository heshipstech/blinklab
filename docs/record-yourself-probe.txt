Record-yourself clip feasibility probe
======================================

Pre-registered 17 September 2026, roadmap row 14.6's probe row, under
amendment 22's marker regime. Committed BEFORE the probe runs, the
stepper-honesty precedent: the outcome section at the end is appended
after the probe, and nothing above it is edited afterwards.

The question
------------

Row 14.6 wants a record-yourself walkthrough: the person records a
short clip of themselves in the browser and the existing clip pipeline
measures it. The probe row asks the only question that matters first:
does a MediaRecorder recording survive the pipeline this project
already trusts, and where it does not, does it fail by NAME rather
than by silently measuring garbage? The later 14.6 rows are gated on
this answer.

The pipeline as read today (all paths read 17 September 2026)
-------------------------------------------------------------

1. Ingestion: src/io/videoFile.ts loadVideoFile(video, file) takes a
   File; a MediaRecorder Blob wraps in one. A clip whose container
   records no duration deliberately reads durationSeconds = Infinity
   ("Reporting 0 would be a lie; the caller decides what an unknown
   duration means to it"). main.ts prints the duration readout only
   when Number.isFinite says so.
2. Stepping: src/io/videoStepper.ts finds the first frame by probing,
   then measureFrameInterval hands up to twelve landed frame times to
   src/core/stepCalibration.ts calibrateStep. Past the tolerances the
   calibration returns {kind: "variableRate"} and the run is REFUSED
   with variableRateRefusal's named sentence — 10.14's provision, the
   named refusal this row's Check cites.
3. Duration-less at the stepper grain: timelineEnd(video) prefers the
   seekable range's end and falls back to video.duration; when neither
   is finite it returns null, and the stepping loop then has NO end
   bound — it steps until a seek stops landing. That is not a named
   refusal; it is an honest walk off the end of the seekable range.

The prediction, committed before the probe runs
-----------------------------------------------

A short webm recorded in Chromium via canvas.captureStream(30) plus
MediaRecorder, wrapped as a File and loaded as a clip:

P1. The container will record no duration: loadVideoFile reports
    durationSeconds = Infinity, and the clip readout prints without a
    duration figure. (The classic streaming-webm shape: MediaRecorder
    writes no Duration element.)
P2. The stepped run will be REFUSED BY NAME on the variable-rate path:
    MediaRecorder stamps frames on the wall clock, so the landed frame
    times will spread past stepCalibration's quantum and tolerance,
    calibrateStep returns variableRate, and the page shows
    variableRateRefusal's sentence. This is the primary predicted
    outcome.
P3. If prediction P2 is wrong — captureStream(30)'s cadence proves
    constant enough to calibrate — the run will instead step to
    wherever Chromium's seekable range ends for a blob URL. Whether
    that end is finite for a MediaRecorder blob is exactly the fact
    the probe exists to record; a run that measures frames and ends
    cleanly is a PASS for feasibility, and a run that misbehaves in
    any unnamed way (wrong count, silent stop, invented timestamps) is
    a defect to be filed, not worked around here.

What gates the later rows
-------------------------

The walkthrough rows of 14.6 proceed only if the probe finds a path a
visitor could actually walk: either the recording measures (P3 pass),
or the refusal it hits is named and legible enough to instruct the
visitor (P2 with the variableRate sentence on screen counts — a
walkthrough can honestly say "your browser's recording is not
constant-rate; use a file instead" — but only the owner can decide
whether that walkthrough is worth shipping). A silent misbehavior
gates everything until fixed. The probe builds NO remedy: no re-mux,
no duration patch, no new ingestion path. It records what the
pipeline this project already trusts does with a recording, by name.
